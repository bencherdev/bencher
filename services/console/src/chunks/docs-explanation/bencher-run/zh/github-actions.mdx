### `--github-actions <GITHUB_TOKEN>`

<br />

可选：设置 GitHub API 身份认证令牌。最方便的方法是使用 [GitHub Actions `GITHUB_TOKEN` 环境变量][github token]（即 `--github-actions ${{ secrets.GITHUB_TOKEN }}`）。

结果将作为 GitHub 检查添加到头提交中，其名称为：

1. `Bencher Report (<ID>)`，如果设置了 [`--ci-id` 选项](#--ci-id-id)
2. `Bencher Report (<项目名称>)`，用于已存在的项目
3. `Bencher Report`，用于 [`--ci-on-the-fly`](#--ci-on-the-fly) 项目（进行中时）

这要求令牌具有 [具备 `write` 权限的 `checks` 范围][github token permissions]。如果无法创建 GitHub 检查，`bencher run` 将记录一条警告并继续。

当 `bencher run` 作为拉取请求的一部分使用时，结果还将作为一条评论添加到拉取请求中。拉取请求上同一项目的所有作业共享这一条评论，每个作业各有一个部分。这要求令牌具有 [具备 `write` 权限的 `pull-requests` 范围][github token permissions]。结果也将始终被添加到作业摘要中。使用 [`--detach` 标志](/zh/docs/explanation/images/#--detach)时，分离的运行不会发布评论，也不会写入作业摘要，而 [`--job` 连接](/zh/docs/explanation/images/#--job-uuid)会完成它所启动的 GitHub 检查（参见 [`--ci-callback-token` 选项](#--ci-callback-token-token)）。

如果设置了 [`--ci-id` 选项](#--ci-id-id)，每个作业的部分以其命名，否则以作业的分支、测试平台和适配器命名。当有两个或更多部分时，评论会为每个部分显示一行摘要及其状态（`Pending`、警报数量、`No Alerts` 或 `Failed`），一张包含所有警报的表格，以及每个部分的结果，这些结果位于可折叠的块中，当该部分有警报时该块默认展开。每个作业保留自己的 GitHub 检查和作业摘要，因此 GitHub 检查名称和必需状态检查不会改变。如果作业的提交已不再是拉取请求的头提交，该作业将保持评论不变。如果令牌无法读取拉取请求，则该作业将记录一条警告，并在不检查头提交的情况下写入评论。

为了找到其他部分，`bencher run` 会列出头提交上的 GitHub 检查，上述具备 `write` 权限的 `checks` 范围已经允许这样做。如果作业无法创建或完成其 GitHub 检查、无法确定拥有该检查的 GitHub App，或无法列出 GitHub 检查，则它将发布一条仅包含其自身结果的评论。来自早期版本 `bencher run` 的该项目评论将被替换：第一个写入共享评论的作业会更新其中最旧的一条并删除其余的。写入共享评论时，作业只会更新或删除由拥有其 GitHub 检查的 GitHub App 发布的评论，使用 `GITHUB_TOKEN` 时即 `github-actions` 机器人。

[github token]: https://docs.github.com/zh/actions/security-guides/automatic-token-authentication
[github token permissions]: https://docs.github.com/zh/actions/security-for-github-actions/security-guides/automatic-token-authentication#permissions-for-the-github_token

> 🐰 如果您在 GitHub Action 中的 Docker 容器内运行，您将需要传入以下环境变量并挂载由 `GITHUB_EVENT_PATH` 指定的路径：
> - `GITHUB_ACTIONS`
> - `GITHUB_EVENT_NAME`
> - `GITHUB_EVENT_PATH`
> - `GITHUB_SHA`
> - `GITHUB_API_URL` (GitHub Enterprise Server 专用)
