## Pull Requests on Bare Metal

A [Bare Metal][bare metal] run holds its GitHub Actions runner for as long as the benchmarks take,
since `bencher run` waits for the Job to finish.
To free the runner, a first workflow submits the Job with [the `--detach` flag][detach option] and exits.
When the Job finishes, Bencher sends a [`repository_dispatch`][github repository_dispatch] event to your repository,
and a second workflow [attaches to the Job][job option] and posts the results as a GitHub Check and a pull request comment,
exactly as an attached run would have.
Using callbacks requires a [Bencher Plus plan][pricing].

> ⚠️ This solution only works if all PRs are from the **same** repository!
> The first workflow needs your repository secrets.
> See [Pull Requests from Forks][pull requests from forks] above.

The event needs a token that outlives the first workflow, since Bencher usually sends it after that workflow's `GITHUB_TOKEN` has expired.
Create a [fine-grained personal access token][github fine-grained token] for the one repository with `Contents` `Read and write` permission,
and add it as a **Repository** secret named `BENCHER_CALLBACK_TOKEN`.
`Contents` write also lets the token push commits to that repository, so never give it access to any other.
Both workflows still pass their own `GITHUB_TOKEN` to `--github-actions`:
only a GitHub App can create or update a GitHub Check,
and both workflows share the GitHub Actions app, which lets the second complete the GitHub Check that the first started.
See [the `--ci-callback-token` docs][ci callback token option] for a full overview.

<PullRequestsOnBareMetalSubmitCode />

1. Create a first GitHub Actions `workflow` file.
   (ex: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Run on `pull_request` events, as in [Pull Requests][pull requests] above.
   (ex: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
3. Create a GitHub Actions `job`.
   (ex: `jobs: submit_pr_benchmarks`)
4. Run on `pull_request` events if and only if the pull request is from the same repository.
   ⚠️ DO NOT REMOVE THIS LINE!
   For handling Fork PRs see [Pull Requests from Forks][pull requests from forks] above.
   (ex: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
5. Set [the permissions for the `GITHUB_TOKEN`][github token permissions]
   to `write` for `checks`.
   The first workflow starts the GitHub Check and posts no comment.
   (ex: `permissions: checks: write`)
6. Set the type of machine the job will run on.
   It only submits the Job, so a small machine is enough.
   (ex: `runs-on: ubuntu-latest`)
7. Checkout the PR branch source code.
   (ex: `uses: actions/checkout@v6`)
8. Install the Bencher CLI using [the GitHub Action][bencher cli github action].
   (ex: `uses: bencherdev/bencher@main`)
9. Use the <code><a href="/docs/explanation/bencher-run/">bencher run</a></code> CLI subcommand
   to submit your pull request branch benchmarks.
   See [the `bencher run` CLI subcommand][bencher run] for a full overview.
   (ex: `bencher run`)
10. Set the `--project` option to the Project slug.
    See [the `--project` docs][project option] for more details.
    (ex: `--project project-abc4567-wxyz123456789`)
11. Set the `--key` option to the `BENCHER_API_KEY` **Repository** secret.
    See [the `--key` docs][key option] for more details.
    (ex: `--key '${{ secrets.BENCHER_API_KEY }}'`)
12. Set the `--branch` option to the PR branch name
    using [the GitHub Actions `GITHUB_HEAD_REF` default environment variable][github default environment variables].
    See [the `--branch` docs][branch option] for a full overview.
    (ex: `--branch "$GITHUB_HEAD_REF"`)
13. Set the Start Point for the PR Branch, as in [Pull Requests][pull requests] above.
    See [the `--start-point` docs][start point] for a full overview.
    (ex: `--start-point "$GITHUB_BASE_REF"`)
14. Set the `--adapter` option to [Bencher Metric Format JSON (`json`)][bmf] that is generated by <code><a href="/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>.
    See [benchmark harness adapters][adapter json] for a full overview.
    (ex: `--adapter json`)
15. Set the `--image` option to your Bare Metal Image.
    See [the `--image` docs][image option] for a full overview.
    (ex: `--image project-abc4567-wxyz123456789:latest`)
16. Set the `--detach` flag to exit as soon as the Job is submitted.
    See [the `--detach` docs][detach option] for more details.
    (ex: `--detach`)
17. Set the `--github-actions` option to the GitHub API authentication token to start the GitHub Check using
    [the GitHub Actions `GITHUB_TOKEN` environment variable][github token].
    See [the `--github-actions` docs][github actions option] for more details.
    (ex: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
18. Set the `--ci-callback-token` option to the `BENCHER_CALLBACK_TOKEN` **Repository** secret,
    so that Bencher can send the `repository_dispatch` event when the Job finishes.
    See [the `--ci-callback-token` docs][ci callback token option] for more details.
    (ex: `--ci-callback-token '${{ secrets.BENCHER_CALLBACK_TOKEN }}'`)
19. Specify the benchmark command to run in the Image.
    The command is passed to the Image's entrypoint, if it has one (see [the `--entrypoint` option][entrypoint option]).
    See [benchmark command][command argument] for a full overview.
    (ex: `bencher mock`)

<PullRequestsOnBareMetalAttachCode />

1. Create a second GitHub Actions `workflow` file on your default branch.
   GitHub only runs a `repository_dispatch` workflow from the default branch,
   so until this file is there, the GitHub Check that the first workflow starts stays in progress.
   (ex: `.github/workflows/pr_bare_metal_benchmarks_attach.yml`)
2. Run on `repository_dispatch` events of the `bencher_run` type.
   See the [GitHub Actions `on` documentation][github actions on]
   and [GitHub Actions `repository_dispatch` documentation][github repository_dispatch] for a full overview.
   (ex: `on: repository_dispatch: types: [bencher_run]`)
3. Create a GitHub Actions `job`.
   (ex: `jobs: attach_pr_benchmarks`)
4. Set [the permissions for the `GITHUB_TOKEN`][github token permissions]
   to `write` for `checks` and `pull-requests`.
   (ex: `permissions: checks: write pull-requests: write`)
5. Set the type of machine the job will run on.
   The Job has already finished, so this job only posts the results.
   (ex: `runs-on: ubuntu-latest`)
6. Install the Bencher CLI using [the GitHub Action][bencher cli github action].
   No checkout is needed.
   (ex: `uses: bencherdev/bencher@main`)
7. Pass the Job UUID from the event through [an intermediate environment variable][github intermediate environment variable],
   never inline in `run:`, as GitHub's script injection guidance says.
   (ex: `env: JOB_UUID: ${{ github.event.client_payload.job }}`)
8. Use the <code><a href="/docs/explanation/bencher-run/">bencher run</a></code> CLI subcommand
   to attach to the Job.
   See [the `bencher run` CLI subcommand][bencher run] for a full overview.
   (ex: `bencher run`)
9. Set the `--project` option to the Project slug.
   If the repository has more than one Project, pass `github.event.client_payload.project` through an environment variable the same way
   and quote it (ex: `--project "$PROJECT_SLUG"`).
   See [the `--project` docs][project option] for more details.
   (ex: `--project project-abc4567-wxyz123456789`)
10. Set the `--key` option to the `BENCHER_API_KEY` **Repository** secret.
    See [the `--key` docs][key option] for more details.
    (ex: `--key '${{ secrets.BENCHER_API_KEY }}'`)
11. Set the `--job` option to the quoted Job UUID.
    See [the `--job` docs][job option] for a full overview.
    (ex: `--job "$JOB_UUID"`)
12. Set the `--error-on-alert` flag to fail the command if an Alert is generated.
    The event carries data only, so options that decide how the results are posted, such as `--ci-only-on-alert` and `--ci-public-links`, go here too, in the second workflow.
    See [the `--error-on-alert` docs][alert err] for a full overview.
    (ex: `--error-on-alert`)
13. Set the `--github-actions` option to the GitHub API authentication token to post results as a GitHub Check and a comment on the Pull Request using
    [the GitHub Actions `GITHUB_TOKEN` environment variable][github token].
    The pull request number, the head commit, the GitHub Check, and the `--ci-id` all come from the event,
    and an explicit `--ci-number` or `--ci-id` here overrides the event.
    See [the `--github-actions` docs][github actions option] for more details.
    (ex: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)

Give each job in the first workflow its own `--ci-id` whenever two of them, such as the entries of a `matrix`,
share a Project, Branch, Testbed, and Adapter on one pull request (ex: `--ci-id '${{ matrix.suite }}'`).
The event carries the `--ci-id` to the second workflow.
Without it, their attaches can post to one comment:
the attach tells a `--build-time` or `--file-size` Job apart by its results, and a failed Job has none.
A `--ci-id` that is exactly a callback body placeholder, such as `{{ job.uuid }}`, arrives as that value, and one with the placeholder shape around any other name, such as `{{ x }}`, fails the run.

A few rules decide what happens to the GitHub Check that the first workflow starts:

- `--detach` with `--github-actions` needs `--ci-callback-token` or an explicit `--callback-url`, and `bencher run` refuses it at parse time without one.
  An empty token, such as an unset repository secret, is refused too.
- Both workflows need a `bencher` CLI that has `--ci-callback-token` and `--job`.
  `bencherdev/bencher@main` installs the latest release unless its `version` input pins another.
- An error in the second workflow's command line, such as a mistyped flag, stops it before it reaches the GitHub Check,
  so the GitHub Check that the first workflow started stays in progress until the second workflow is fixed and run again.
- A fine-grained personal access token expires.
  When `BENCHER_CALLBACK_TOKEN` does, every callback fails with a `401` and every GitHub Check that the first workflow starts stays in progress.
  Each Job keeps the token it was submitted with, so rotate the token well before it expires, and keep the old token valid until every Job submitted with it has finished.
- If the Job failed or was canceled, the second workflow completes the GitHub Check as `failure` or `cancelled` and posts the pull request comment under the usual rules (so `--ci-only-on-alert` still skips a first comment).
  The Job's error is in the second workflow's log, not in the GitHub Check.
- If the Organization is not on a Bencher Plus plan, the callback is skipped.
  The first workflow completes the GitHub Check as `neutral` with the reason (ex: `callback skipped: requires a Bencher Plus plan`).
- If the first workflow cannot read the Job back after submitting it, it prints a warning and leaves the GitHub Check in progress for the second workflow to complete.
- Outside GitHub Actions, `--ci-callback-token` is ignored.
- On GitHub Enterprise Server, the API URL (`GITHUB_API_URL`) must be reachable over `https`, at a public address, from the Bencher server that sends the callback.
