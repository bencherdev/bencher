## Pull Requests en hardware dedicado

GitHub Actions tiene runners Self-Hosted, pero requieren que uses
su ruidoso binario [GitHub Actions Runner][github actions runner].
[Bencher Bare Metal][bare metal] ejecuta benchmarks en una flota dedicada de hardware bare metal
usando un runner de benchmarks de bajo ruido diseñado específicamente para ello.
Además, Bencher Bare Metal admite PRs desde forks,
mientras que el GitHub Actions Runner no.

Una vez que te hayas pasado a Bencher Bare Metal,
no querrás tener un trabajo de GitHub Actions en ejecución mientras espera a Bencher.
Para resolverlo, el workflow envía el Job de Bencher Bare Metal y termina.
Cuando el Job termina, Bencher mismo completa la Verificación de GitHub
y publica los resultados como un comentario en la Pull Request.

El siguiente ejemplo sirve para ramas dentro del **mismo** repositorio.
Usa este patrón junto con
el workflow de [Pull Requests desde Forks][pull requests from forks] más arriba
para obtener benchmarks en hardware dedicado para las PRs desde forks.

Primero, vincula el repositorio al Proyecto, una sola vez:

1. En la Consola de Bencher, abre los `Settings` del Proyecto y luego `Connections`.
2. En la tarjeta de GitHub, haz clic en `Link repository`.
   GitHub te devuelve a `Connections`, donde la tarjeta lista cada repositorio al que puedes hacer push.
3. Haz clic en `Link` junto al repositorio.
   Si no aparece en la lista, haz clic en `Install on GitHub` y dale a la aplicación acceso a él.
   Si muestra `Approval required`, haz clic en `Approve on GitHub`, aprueba los nuevos permisos de la aplicación
   y luego vuelve a abrir `Connections` y haz clic en `Link repository`.

Para vincularlo necesitas el rol Maintainer en el Proyecto, que tienen los Leaders de la Organización y los administradores del servidor, y acceso de push al repositorio.
La aplicación de GitHub de Bencher necesita acceso de lectura y escritura a los checks y las pull requests del repositorio,
y acceso de lectura a su contenido, así que no puede hacer push al repositorio.
Bencher crea un token para el repositorio vinculado
y publica con él la Verificación de GitHub y el comentario en la Pull Request.
Si la tarjeta de GitHub muestra `Disconnected`, haz clic en `Install on GitHub` y vuelve a dar a la aplicación acceso al repositorio,
o reactiva su instalación suspendida, y el vínculo se restablece.
Para Bencher Self-Hosted, el servidor necesita [su propia aplicación de GitHub][github app] y la versión `v0.6.18` o posterior.
Con una licencia de Bencher Plus Enterprise, un servidor de Bencher Self-Hosted puede usar [GitHub Enterprise Server][github enterprise server] en lugar de github.com.

> 🐰 Cualquiera que tenga la clave de API del Proyecto puede hacer que Bencher publique una Verificación de GitHub o un comentario en una Pull Request
> del repositorio vinculado, en cualquier commit o Pull Request de él.
> Mantén el `BENCHER_API_KEY` en secreto como cualquier otro secreto.

1. Crea un archivo de `workflow` de GitHub Actions.
   (ej: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Nombra este flujo de trabajo.
   (ej: `name: Bare Metal PR Benchmarks with Bencher`)
3. Ejecuta en eventos de `pull_request`, como en [Pull Requests][pull requests] más arriba.
   (ej: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. Crea un `job` de GitHub Actions.
   (ej: `jobs: submit_pr_benchmarks`)
5. Ejecuta en eventos de `pull_request` si y solo si la pull request es del mismo repositorio.
   ⚠️ ¡NO ELIMINES ESTA LÍNEA!
   Para manejar PRs de Forks, consulta [Pull Requests desde Forks][pull requests from forks] más arriba.
   (ej: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. Establece [los permisos para el `GITHUB_TOKEN`][github token permissions]
   en `read` para `contents`.
   Bencher publica la Verificación de GitHub y el comentario, así que el workflow no necesita acceso de escritura.
   (ej: `permissions: contents: read`)
7. Establece el tipo de máquina en la que se ejecutará el trabajo.
   Solo envía el Job, así que basta con una máquina pequeña.
   (ej: `runs-on: ubuntu-latest`)
8. Clona el código fuente de la rama PR.
   (ej: `uses: actions/checkout@v6`)
9. Instala el Bencher CLI usando [la GitHub Action][bencher cli github action].
   (ej: `uses: bencherdev/bencher@main`)
10. Usa el subcomando CLI <code><a href="/es/docs/explanation/bencher-run/">bencher run</a></code>
    para enviar tus benchmarks de la rama de la pull request.
    Consulta [el subcomando CLI `bencher run`][bencher run] para una visión completa.
    (ej: `bencher run`)
11. Establece la opción `--project` al slug del Proyecto.
    Consulta [los documentos de `--project`][project option] para más detalles.
    (ej: `--project project-abc4567-wxyz123456789`)
12. Establece la opción `--key` al secreto **Repository** `BENCHER_API_KEY`.
    Consulta [los documentos de `--key`][key option] para más detalles.
    (ej: `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. Establece la opción `--branch` al nombre de la rama PR
    usando [la variable de entorno predeterminada `GITHUB_HEAD_REF` de GitHub Actions][github default environment variables].
    Consulta [los documentos de `--branch`][branch option] para una visión completa.
    (ej: `--branch "$GITHUB_HEAD_REF"`)
14. Establece la opción `--hash` al hash `git` de la rama PR, como en [Pull Requests][pull requests] más arriba.
    Consulta [los documentos de `--hash`][hash option] para una visión completa.
    (ej: `--hash '${{ github.event.pull_request.head.sha }}'`)
15. Establece el Punto de Inicio para la Rama PR, como en [Pull Requests][pull requests] más arriba.
    Consulta [los documentos de `--start-point`][start point] para una visión completa.
    (ej: `--start-point "$GITHUB_BASE_REF"`)
16. Establece la opción `--adapter` al [Formato de Métrica Bencher JSON (`json`)][bmf] que es generado por <code><a href="/es/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>.
    Consulta [adaptadores de harness de benchmark][adapter json] para una visión completa.
    (ej: `--adapter json`)
17. Establece la opción `--image` a tu imagen para hardware dedicado.
    Consulta [los documentos de `--image`][image option] para una visión completa.
    (ej: `--image project-abc4567-wxyz123456789:latest`)
18. Establece la bandera `--detach` para terminar en cuanto se envíe el Job.
    Consulta [los documentos de `--detach`][detach option] para más detalles.
    (ej: `--detach`)
19. Establece la opción `--github-actions` a [la variable de entorno `GITHUB_TOKEN` de GitHub Actions][github token].
    Con `--detach`, `bencher run` envía el repositorio, el commit head y el número de la Pull Request
    del evento de GitHub Actions con el Job, y no hace ninguna petición a GitHub con el token.
    Consulta [los documentos de `--github-actions`][github actions option] para más detalles.
    (ej: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. Especifica el comando de benchmark que se ejecuta en la imagen.
    El comando se pasa al entrypoint de la imagen, si tiene uno (consulta [la opción `--entrypoint`][entrypoint option]).
    Consulta [comando de benchmark][command argument] para una visión completa.
    (ej: `bencher mock`)

Bencher rechaza enviar el Job si no puede publicar los resultados:
el servidor no tiene una aplicación de GitHub, el Proyecto no está reclamado,
o el Proyecto no tiene un repositorio vinculado y conectado para el repositorio del workflow.
Después del envío, Bencher inicia la Verificación de GitHub en el commit head.
Cuando el Job termina, Bencher completa la Verificación de GitHub y luego escribe el comentario en la Pull Request,
como describe [la opción `--github-actions`][github actions option].
La Verificación de GitHub concluye como fallida si el Informe tiene una Alerta o el Job falla,
así que [la bandera `--error-on-alert`][alert err] no es necesaria, y entra en conflicto con `--detach`.
Las opciones que deciden cómo se publican los resultados, como `--ci-only-on-alert` y `--ci-id`, van en el mismo comando,
y Bencher las guarda con el Job.

La Verificación de GitHub pertenece a la aplicación de GitHub de Bencher, no a GitHub Actions.
Si una regla de protección de rama o un conjunto de reglas [requiere la Verificación de GitHub][github required status checks],
establece la aplicación de GitHub de Bencher como su origen.
De lo contrario, GitHub espera una Verificación de GitHub de GitHub Actions que nunca llega.

Si la instalación de la aplicación de GitHub de Bencher no ha aprobado sus nuevos permisos, Bencher no puede publicar los resultados.
El Job registra el fallo con un enlace para aprobarlos,
y `bencher run` imprime el enlace si ve el fallo antes de terminar.
Una vez aprobados los permisos, la siguiente ejecución publica sus resultados.

Un Job sin Pull Request, como uno de un evento `push`, obtiene una Verificación de GitHub y ningún comentario.
Lo mismo ocurre con un Job cuyo commit ya no es el head de la Pull Request.
Si la Pull Request también tiene ejecuciones del Proyecto sin `--detach`,
obtiene un segundo comentario para ellas, del bot de GitHub Actions.
