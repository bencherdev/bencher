## Bencher Bare Metal을 꿈꾸며

Bencher를 시작한 아주 초창기부터, 저는 베어 메탈 벤치마킹 플릿을 만드는 꿈을 꿔 왔습니다. 전통적인 CI 러너는 가상 머신이라는 특성상 노이즈가 너무 커서 일관된 벤치마크 결과를 얻을 수 없습니다. 예를 들어 지연 시간이 200% 늘어난 것은 감지할 수 있어도, 20% 늘어난 것을 안정적으로 감지하기는 불가능합니다. CI에서 벤치마킹하는 한 가지 방법으로 명령어 카운트가 있습니다. 명령어 카운트는 대체로 결정적입니다. 하지만 명령어 카운트는 여러분이 실제로 신경 쓰는 것, 즉 벽시계 시간의 대리 지표일 뿐입니다. "CPU 시뮬레이션" 안에서 실행되어 명령어 카운트를 뱉어 내는 것은 무엇이든 속도와 상관관계만 가질 수 있습니다. 문제는 실제로 베어 메탈에서 측정해 보기 전까지는 그 값이 얼마나 많이, 혹은 얼마나 적게 어긋나 있는지 결코 알 수 없다는 것입니다.

Bencher의 가장 초기 사용자 중 하나가 [Rustls 프로젝트][rustls case study]였습니다. 저는 그들의 [Rustls bench runner][github rustls bench app]에 기여하는 것을 도왔습니다. 하지만 이것은 베어 메탈 벤치마킹 플릿을 쌓아 올릴 좋은 기반이 아니었습니다. 단일 호스트에서 돌아갔고 모든 벤치마크 워크로드를 신뢰할 수 있다고 간주했습니다. 즉, 포크에서 온 PR도 안 되고 멀티테넌시도 안 된다는 뜻입니다. 게다가 대부분의 팀은 베어 메탈 벤치마킹 서버 한 대당 매달 $100 이상을 내고 싶어 하지 않습니다.

오케스트레이션 계층으로 GitHub Actions를 쓰는 것도 고려했지만, 이 접근 방식에는 몇 가지 근본적인 한계가 있었습니다. 우선 [GitHub Actions Runner][github actions runner]는 C#으로 작성되어 있습니다. 즉, 실행 도중에 가비지 컬렉터가 돌기 시작해서 벤치마크 결과를 왜곡할 수 있습니다. 아, 그리고 실행 도중에 돌지 않도록 [자동 업데이트 기능][runner auto updater]을 꼭 꺼 두세요. 그렇다고 너무 오래 잊고 있으면 안 됩니다. 안 그러면 작업이 더 이상 실행되지 않을 테니까요!

설령 GitHub Actions Runner가 조용하고 깔끔한 Rust 바이너리였다고 해도, 더 근본적인 문제는 그것이 GitHub Actions에 묶여 있다는 점이었습니다. Bencher는 처음부터 CLI 우선이었습니다. 좋든 나쁘든, 저는 Bencher를 특정 CI 제공자 하나에 너무 깊이 묶고 싶지 않았습니다. [Bencher CLI GitHub Action][github action bencher cli]이 있긴 하지만, 하는 일이라고는 CLI를 설치해 주는 것뿐입니다. 저는 Bencher Bare Metal이 GitHub Actions에서만이 아니라 CLI가 동작하는 곳이라면 어디서든 동작하기를 원했습니다.

제가 떠올린 아이디어는 OCI 이미지로 벤치마킹 워크로드를 묶고, 선택 사항인 아주 작은 샌드박스를 사용해 특정 베어 메탈 호스트에서 한 번에 오직 하나의 작업만 실행하는 것이었습니다. 이것을 밤과 주말에 혼자 만들어 낸다는 생각은 막막했습니다. 본업과 가족이 있는 상황에서, 혼자 조금씩 깎아 나갔다면 최소 1년은 걸렸을 겁니다.
