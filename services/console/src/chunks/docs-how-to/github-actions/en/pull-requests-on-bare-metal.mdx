## Pull Requests on Bare Metal

GitHub Actions has Self-Hosted runners, but they require you to use
their noisy [GitHub Actions Runner][github actions runner] binary.
[Bencher Bare Metal][bare metal] runs benchmarks on a dedicated fleet of bare metal hardware
using a purpose built, low-noise benchmark runner.
Additionally, Bencher Bare Metal supports PRs from forks,
while the GitHub Actions Runner does not.

Once you've made the switch to Bencher Bare Metal,
you don't want to have a GitHub Actions job running while it waits for Bencher.
To solve this, the workflow submits the Bencher Bare Metal Job and exits.
When the Job finishes, Bencher itself completes the GitHub Check
and posts the results as a comment on the pull request.

The following example is for use for branches within the **same** repository.
Use this pattern in conjunction with
the [Pull Requests from Forks][pull requests from forks] workflow above
to get bare metal benchmarking for fork PRs.

First, link the repository to the Project, once:

1. In the Bencher Console, open the Project's `Settings`, then `Connections`.
2. On the GitHub card, click `Link repository`.
   GitHub brings you back to `Connections`, where the card lists each repository you can push to.
3. Click `Link` beside the repository.
   If it is not listed, click `Install on GitHub` and give the app access to it.
   If it shows `Approval required`, click `Approve on GitHub` and approve the app's new permissions,
   then open `Connections` again and click `Link repository`.

Linking needs the Maintainer role on the Project, which Organization Leaders and server admins hold, and push access to the repository.
Bencher's GitHub App needs read and write access to the repository's checks and pull requests,
and read access to its contents, so it cannot push to the repository.
Bencher creates a token for the linked repository
and posts the GitHub Check and the pull request comment with it.
If the GitHub card shows `Disconnected`, click `Install on GitHub` and give the app access to the repository again,
or unsuspend its installation, and the link reconnects.
For Bencher Self-Hosted, the server needs [its own GitHub App][github app] and version `v0.6.18` or later.

> 🐰 Anyone with the Project's API key can make Bencher post a GitHub Check or a pull request comment
> to the linked repository, on any commit or pull request in it.
> Keep the `BENCHER_API_KEY` secret like any other.

1. Create a GitHub Actions `workflow` file.
   (ex: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Name this workflow.
   (ex: `name: Bare Metal PR Benchmarks with Bencher`)
3. Run on `pull_request` events, as in [Pull Requests][pull requests] above.
   (ex: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. Create a GitHub Actions `job`.
   (ex: `jobs: submit_pr_benchmarks`)
5. Run on `pull_request` events if and only if the pull request is from the same repository.
   ⚠️ DO NOT REMOVE THIS LINE!
   For handling Fork PRs see [Pull Requests from Forks][pull requests from forks] above.
   (ex: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. Set [the permissions for the `GITHUB_TOKEN`][github token permissions]
   to `read` for `contents`.
   Bencher posts the GitHub Check and the comment, so the workflow needs no write access.
   (ex: `permissions: contents: read`)
7. Set the type of machine the job will run on.
   It only submits the Job, so a small machine is enough.
   (ex: `runs-on: ubuntu-latest`)
8. Checkout the PR branch source code.
   (ex: `uses: actions/checkout@v6`)
9. Install the Bencher CLI using [the GitHub Action][bencher cli github action].
   (ex: `uses: bencherdev/bencher@main`)
10. Use the <code><a href="/docs/explanation/bencher-run/">bencher run</a></code> CLI subcommand
    to submit your pull request branch benchmarks.
    See [the `bencher run` CLI subcommand][bencher run] for a full overview.
    (ex: `bencher run`)
11. Set the `--project` option to the Project slug.
    See [the `--project` docs][project option] for more details.
    (ex: `--project project-abc4567-wxyz123456789`)
12. Set the `--key` option to the `BENCHER_API_KEY` **Repository** secret.
    See [the `--key` docs][key option] for more details.
    (ex: `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. Set the `--branch` option to the PR branch name
    using [the GitHub Actions `GITHUB_HEAD_REF` default environment variable][github default environment variables].
    See [the `--branch` docs][branch option] for a full overview.
    (ex: `--branch "$GITHUB_HEAD_REF"`)
14. Set the `--hash` option to the PR branch `git` hash, as in [Pull Requests][pull requests] above.
    See [the `--hash` docs][hash option] for a full overview.
    (ex: `--hash '${{ github.event.pull_request.head.sha }}'`)
15. Set the Start Point for the PR Branch, as in [Pull Requests][pull requests] above.
    See [the `--start-point` docs][start point] for a full overview.
    (ex: `--start-point "$GITHUB_BASE_REF"`)
16. Set the `--adapter` option to [Bencher Metric Format JSON (`json`)][bmf] that is generated by <code><a href="/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>.
    See [benchmark harness adapters][adapter json] for a full overview.
    (ex: `--adapter json`)
17. Set the `--image` option to your Bare Metal Image.
    See [the `--image` docs][image option] for a full overview.
    (ex: `--image project-abc4567-wxyz123456789:latest`)
18. Set the `--detach` flag to exit as soon as the Job is submitted.
    See [the `--detach` docs][detach option] for more details.
    (ex: `--detach`)
19. Set the `--github-actions` option to [the GitHub Actions `GITHUB_TOKEN` environment variable][github token].
    With `--detach`, `bencher run` sends the repository, the head commit, and the pull request number
    from the GitHub Actions event with the Job, and makes no GitHub request with the token.
    See [the `--github-actions` docs][github actions option] for more details.
    (ex: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. Specify the benchmark command to run in the Image.
    The command is passed to the Image's entrypoint, if it has one (see [the `--entrypoint` option][entrypoint option]).
    See [benchmark command][command argument] for a full overview.
    (ex: `bencher mock`)

Bencher refuses to submit the Job if it cannot post the results:
the server has no GitHub App, the Project is unclaimed,
or the Project has no connected linked repository for the workflow's repository.
After the submit, Bencher starts the GitHub Check on the head commit.
When the Job finishes, Bencher completes the GitHub Check and then writes the pull request comment,
as [the `--github-actions` option][github actions option] describes.
The GitHub Check concludes as a failure if the Report has an Alert or the Job fails,
so [the `--error-on-alert` flag][alert err] is not needed, and it conflicts with `--detach`.
Options that decide how the results are posted, such as `--ci-only-on-alert` and `--ci-id`, go on the same command,
and Bencher keeps them with the Job.

The GitHub Check belongs to Bencher's GitHub App, not to GitHub Actions.
If a branch protection rule or ruleset [requires the GitHub Check][github required status checks],
set Bencher's GitHub App as its source.
Otherwise, GitHub waits for a GitHub Check from GitHub Actions that never comes.

If the installation of Bencher's GitHub App has not approved its new permissions, Bencher cannot post the results.
The Job records the failure with a link to approve them,
and `bencher run` prints the link if it sees the failure before it exits.
Once the permissions are approved, the next run posts its results.

A Job with no pull request, such as from a `push` event, gets a GitHub Check and no comment.
So does a Job whose commit is no longer the head of the pull request.
If the pull request also has runs of the Project without `--detach`,
it gets a second comment for them, from the GitHub Actions bot.
