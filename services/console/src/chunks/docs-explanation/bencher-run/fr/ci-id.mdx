### `--ci-id <ID>`

<br />

Optionnel : ID personnalisé pour publier des résultats sur CI.  
Tous les travaux d'un Projet sur une pull request partagent un seul commentaire, avec une ligne de Rapport pour chaque travail.  
Avec un ID, le libellé de la ligne est son numéro et l'ID (ex : `2 (microbench)`).  
Tant que le Rapport du travail n'existe pas, sa ligne n'affiche que l'ID et aucun numéro (ex : `(microbench)`), comme `Pending` tant que le travail s'exécute, et vient après les lignes numérotées.  
Sans ID, le libellé est le numéro seul, et la ligne apparaît dès que le Rapport du travail existe.  
Par défaut, des travaux partagent une ligne lorsqu'ils ont la même combinaison de : Branche, Banc d'essai et [Adaptateur](/fr/docs/explanation/adapters/),  
ainsi que [`--build-time`](#--build-time) et [`--file-size`](#--file-size-file) s'ils sont définis.  
Définir un ID personnalisé est utile lorsque Bencher est exécuté plusieurs fois sur le même commit pour la même combinaison de Projet, Branche, Banc d'essai et Adaptateur,  
afin que chaque exécution ait sa propre ligne.  
Par exemple, une exécution `push` et une exécution `pull_request` sur la même branche partagent le commit de tête,  
donnez donc à chaque exécution son propre ID, ou n'utilisez pas `--github-actions` pour l'exécution `push`.  
Sinon, les exécutions partagent une ligne, qui n'en affiche qu'une seule, et une exécution plus ancienne n'écrit rien dès qu'une exécution plus récente occupe la ligne.  
L'ID est également utilisé à la place du nom du Projet dans le nom de la vérification GitHub (c'est-à-dire `Bencher Report (<ID>)`),  
de sorte que chaque invocation obtient un nom stable qui peut être utilisé comme vérification de statut requise distincte.  
Nécessite : `--github-actions`
