## Pull Requests sur matériel dédié

GitHub Actions propose des runners auto-hébergés, mais ils vous obligent à utiliser
leur binaire bruyant [GitHub Actions Runner][github actions runner].
[Bencher Bare Metal][bare metal] exécute les benchmarks sur une flotte dédiée de matériel bare metal
à l'aide d'un runner de benchmark à faible bruit, conçu sur mesure.
De plus, Bencher Bare Metal prend en charge les PRs de forks,
alors que le GitHub Actions Runner ne le fait pas.

Une fois que vous êtes passé à Bencher Bare Metal,
vous ne voulez pas qu'un job GitHub Actions tourne pendant qu'il attend Bencher.
Pour résoudre ce problème, Bencher utilise un workflow scindé afin que GitHub Actions
puisse attendre les Jobs Bencher Bare Metal de manière asynchrone.

L'exemple suivant est destiné aux branches au sein du **même** dépôt.
Utilisez ce modèle conjointement avec
le workflow [Pull Requests depuis des Forks][pull requests from forks] ci-dessus
pour obtenir le benchmarking sur matériel dédié pour les PRs de forks.

<PullRequestsOnBareMetalSubmitCode />

1. Créez un premier fichier `workflow` GitHub Actions.
   (ex : `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Nommez ce workflow.
   (ex : `name: Bare Metal PR Benchmarks with Bencher`)
3. Exécutez sur des événements `pull_request`, comme dans [Pull Requests][pull requests] ci-dessus.
   (ex : `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. Créez un `job` GitHub Actions.
   (ex : `jobs: submit_pr_benchmarks`)
5. Exécutez sur des événements `pull_request` uniquement si la pull request vient du même dépôt.
   ⚠️ NE SUPPRIMEZ PAS CETTE LIGNE !
   Pour gérer les PRs de Forks, voir [Pull Requests depuis des Forks][pull requests from forks] ci-dessus.
   (ex : `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. Définissez [les permissions pour le `GITHUB_TOKEN`][github token permissions]
   sur `write` pour les `checks`.
   Le premier workflow démarre la vérification GitHub et ne publie aucun commentaire.
   (ex : `permissions: checks: write`)
7. Définissez le type de machine sur laquelle le job s'exécutera.
   Il ne fait que soumettre le Job, donc une petite machine suffit.
   (ex : `runs-on: ubuntu-latest`)
8. Récupérez le code source de la branche PR.
   (ex : `uses: actions/checkout@v6`)
9. Installez le Bencher CLI en utilisant [l'Action GitHub][bencher cli github action].
   (ex : `uses: bencherdev/bencher@main`)
10. Utilisez la sous-commande CLI <code><a href="/fr/docs/explanation/bencher-run/">bencher run</a></code>
    pour soumettre vos benchmarks de branche de pull request.
    Voir [la sous-commande CLI `bencher run`][bencher run] pour un aperçu complet.
    (ex : `bencher run`)
11. Définissez l'option `--project` sur le slug du projet.
    Voir [la documentation `--project`][project option] pour plus de détails.
    (ex : `--project project-abc4567-wxyz123456789`)
12. Définissez l'option `--key` sur le secret du **dépôt** `BENCHER_API_KEY`.
    Voir [la documentation `--key`][key option] pour plus de détails.
    (ex : `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. Définissez l'option `--branch` sur le nom de la branche PR
    en utilisant [la variable d'environnement par défaut `GITHUB_HEAD_REF` de GitHub Actions][github default environment variables].
    Voir [la documentation `--branch`][branch option] pour un aperçu complet.
    (ex : `--branch "$GITHUB_HEAD_REF"`)
14. Définissez le point de départ de la branche PR, comme dans [Pull Requests][pull requests] ci-dessus.
    Voir [la documentation `--start-point`][start point] pour un aperçu complet.
    (ex : `--start-point "$GITHUB_BASE_REF"`)
15. Définissez l'option `--adapter` sur le [Format de Métrique Bencher JSON (`json`)][bmf] généré par <code><a href="/fr/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>.
    Voir [les adaptateurs de harnais de benchmark][adapter json] pour un aperçu complet.
    (ex : `--adapter json`)
16. Définissez l'option `--image` sur votre image pour matériel dédié.
    Voir [la documentation `--image`][image option] pour un aperçu complet.
    (ex : `--image project-abc4567-wxyz123456789:latest`)
17. Définissez le drapeau `--detach` pour vous terminer dès que le Job est soumis.
    Voir [la documentation `--detach`][detach option] pour plus de détails.
    (ex : `--detach`)
18. Définissez l'option `--github-actions` sur le token d'authentification de l'API GitHub pour démarrer la vérification GitHub en utilisant
    [la variable d'environnement `GITHUB_TOKEN` de GitHub Actions][github token].
    Voir [la documentation `--github-actions`][github actions option] pour plus de détails.
    (ex : `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
19. Définissez l'option `--ci-callback-token` sur le secret du **dépôt** `BENCHER_CALLBACK_TOKEN`,
    afin que Bencher puisse envoyer l'événement `repository_dispatch` lorsque le Job se termine.
    Voir [la documentation `--ci-callback-token`][ci callback token option] pour plus de détails.
    (ex : `--ci-callback-token '${{ secrets.BENCHER_CALLBACK_TOKEN }}'`)
20. Spécifiez la commande de benchmark à exécuter dans l'image.
    La commande est transmise au point d'entrée de l'image, s'il y en a un (voir [l'option `--entrypoint`][entrypoint option]).
    Voir [la commande de benchmark][command argument] pour un aperçu complet.
    (ex : `bencher mock`)

<PullRequestsOnBareMetalAttachCode />

1. Créez un second fichier `workflow` GitHub Actions sur votre branche par défaut.
   GitHub n'exécute un workflow `repository_dispatch` que depuis la branche par défaut,
   donc tant que ce fichier n'y est pas, la vérification GitHub que démarre le premier workflow reste en cours.
   (ex : `.github/workflows/pr_bare_metal_benchmarks_attach.yml`)
2. Nommez ce workflow.
   (ex : `name: Attach Bare Metal PR Benchmarks with Bencher`)
3. Exécutez sur des événements `repository_dispatch` du type `bencher_run`.
   Consultez la [documentation de GitHub Actions `on`][github actions on]
   et la [documentation de GitHub Actions `repository_dispatch`][github repository_dispatch] pour un aperçu complet.
   (ex : `on: repository_dispatch: types: [bencher_run]`)
4. Créez un `job` GitHub Actions.
   (ex : `jobs: attach_pr_benchmarks`)
5. Définissez [les permissions pour le `GITHUB_TOKEN`][github token permissions]
   sur `write` pour les `checks` et `pull-requests`.
   (ex : `permissions: checks: write pull-requests: write`)
6. Définissez le type de machine sur laquelle le job s'exécutera.
   Le Job est déjà terminé, donc ce job ne fait que publier les résultats.
   (ex : `runs-on: ubuntu-latest`)
7. Installez le Bencher CLI en utilisant [l'Action GitHub][bencher cli github action].
   Aucun checkout n'est nécessaire.
   (ex : `uses: bencherdev/bencher@main`)
8. Transmettez l'UUID du Job de l'événement par [une variable d'environnement intermédiaire][github intermediate environment variable],
   jamais directement dans `run:`, comme le recommandent les consignes de GitHub contre l'injection de script.
   (ex : `env: JOB_UUID: ${{ github.event.client_payload.bencher.job }}`)
9. Utilisez la sous-commande CLI <code><a href="/fr/docs/explanation/bencher-run/">bencher run</a></code>
   pour vous rattacher au Job.
   Voir [la sous-commande CLI `bencher run`][bencher run] pour un aperçu complet.
   (ex : `bencher run`)
10. Définissez l'option `--project` sur le slug du projet.
    Si le dépôt a plus d'un Projet, transmettez `github.event.client_payload.bencher.project` de la même façon par une variable d'environnement
    et mettez-la entre guillemets (ex : `--project "$PROJECT_SLUG"`).
    Voir [la documentation `--project`][project option] pour plus de détails.
    (ex : `--project project-abc4567-wxyz123456789`)
11. Définissez l'option `--key` sur le secret du **dépôt** `BENCHER_API_KEY`.
    Voir [la documentation `--key`][key option] pour plus de détails.
    (ex : `--key '${{ secrets.BENCHER_API_KEY }}'`)
12. Définissez l'option `--job` sur l'UUID du Job entre guillemets.
    Voir [la documentation `--job`][job option] pour un aperçu complet.
    (ex : `--job "$JOB_UUID"`)
13. Définissez le drapeau `--error-on-alert` pour échouer la commande si une Alerte est générée.
    L'événement ne transporte que des données, donc les options qui décident de la façon dont les résultats sont publiés, comme `--ci-only-on-alert` et `--ci-public-links`, vont aussi ici, dans le second workflow.
    Voir [la documentation `--error-on-alert`][alert err] pour un aperçu complet.
    (ex : `--error-on-alert`)
14. Définissez l'option `--github-actions` sur le token d'authentification de l'API GitHub pour poster les résultats en tant que vérification GitHub et commentaire sur la Pull Request en utilisant
    [la variable d'environnement `GITHUB_TOKEN` de GitHub Actions][github token].
    Un `--ci-number` ou un `--ci-id` explicite ici a priorité sur l'événement.
    Voir [la documentation `--github-actions`][github actions option] pour plus de détails.
    (ex : `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
