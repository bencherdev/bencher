### `--ci-id <ID>`

<br />

Optionnel : ID personnalisé pour publier des résultats sur CI.  
Tous les travaux d'un Projet sur une pull request partagent un seul commentaire, et l'ID nomme la section du travail dans ce commentaire.  
Avec un ID, la section du travail s'affiche comme `Pending` pendant l'exécution du travail.  
Sans ID, la section apparaît une fois le Rapport du travail créé.  
Par défaut, la section d'un travail est nommée d'après la combinaison de : Branche, Banc d'essai et [Adaptateur](/fr/docs/explanation/adapters/),  
ainsi que [`--build-time`](#--build-time) et [`--file-size`](#--file-size-file) s'ils sont définis.  
Définir un ID personnalisé est utile lorsque Bencher est exécuté plusieurs fois sur le même commit pour la même combinaison de Projet, Branche, Banc d'essai et Adaptateur,  
afin que chaque exécution ait sa propre section.  
Par exemple, une exécution `push` et une exécution `pull_request` sur la même branche partagent le commit de tête,  
donnez donc à chaque exécution son propre ID, ou n'utilisez pas `--github-actions` pour l'exécution `push`.  
Sinon, seule la section du travail le plus récent peut apparaître, et l'autre travail n'écrit rien.  
L'ID est également utilisé à la place du nom du Projet dans le nom de la vérification GitHub (c'est-à-dire `Bencher Report (<ID>)`),  
de sorte que chaque invocation obtient un nom stable qui peut être utilisé comme vérification de statut requise distincte.  
Nécessite : `--github-actions`
