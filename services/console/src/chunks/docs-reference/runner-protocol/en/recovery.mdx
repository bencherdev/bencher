## Timeouts & Recovery

Three complementary mechanisms ensure a Job never gets stuck,
even if a Runner crashes or loses its connection.

### Heartbeat Timeout

While the connection is open, a read timeout detects a Runner that is connected but silent.
Only valid protocol messages reset the timer;
invalid JSON, ping/pong frames, and binary messages do not.
On timeout, a Job that has run longer than its timeout plus a grace period is marked `canceled`,
and otherwise the execution is marked `unknown` (contact with the Runner was lost).
No further execution of the Job is sent while one is `unknown`,
and the Job is `unknown` while it has no other execution in flight.

### Hard Job Timeout

The server enforces a hard maximum execution duration independent of Runner behavior,
so a buggy or compromised Runner cannot run indefinitely by sending heartbeats.
The Job timeout bounds the time inside the Job's own executions, summed:
each execution counts from its `running` to its result,
and the time between executions, when other Jobs run, does not count.
Each `job` message carries what is left of the Job timeout as its timeout.
When the sum exceeds the limit (the Job timeout plus a grace period),
the Job is marked `canceled` and its Runners receive a `cancel` message.
A Job whose time runs out before its last iteration is marked `failed`,
with an error that names how many of its iterations ran.
Set `--job-timeout` for a Job of many iterations.

### Disconnect Recovery

If the connection drops while an execution is still in flight,
the server schedules a check after the heartbeat timeout.
If the Runner has reconnected and resumed heartbeats, the execution continues;
otherwise the execution is marked `unknown`, or the Job `canceled` if it had exceeded the hard timeout.
The server checks an `unknown` execution again at its deadline:
the time it was sent with plus the grace period, counted from when it started.
An execution is never sent again to another Runner.
On startup, the server also marks orphaned executions that were sent but never started `unknown`,
reschedules timeouts for executions in flight,
leaves a Job between its executions `running` for its next execution,
and re-processes `completed` Jobs whose results were stored but not yet parsed;
a `completed` Job whose results were lost is marked `unknown` so the Runner can resend them.

### Reconnection & Result Delivery

Reconnection is supported and idempotent.
Resending `running` for an already-running Job only refreshes its liveness,
and resending a terminal `completed`, `failed`, or `canceled` message is always safe.
Terminal messages carry the execution's UUID and receive an `ack`;
if the connection drops before the `ack` arrives,
the Runner stores the result and resends it on the next connection before going idle.
A Runner's result resolves an `unknown` execution until its deadline passes, and its Job goes on.
A `failed` or `canceled` Job never changes state again: a late result is acknowledged, so the Runner stops resending it, and discarded.

### No Automatic Retry

A `failed` Job is not retried automatically.
A failed benchmark is signal, not an error to hide,
so re-running it is left to you.
