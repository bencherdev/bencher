### `plus.oauth`

Этот раздел позволяет MCP-клиентам, таким как ChatGPT, claude.ai и Claude Code, [входить в Bencher MCP](/ru/docs/how-to/mcp/) через OAuth.
API-сервер становится для них сервером авторизации OAuth, а пользователи одобряют каждое приложение в Bencher Console по адресу `console.url`.
Весь раздел является необязательным.
Если он не указан, OAuth выключен: его эндпоинты возвращают `404 Not Found`, а Bencher MCP принимает только API-ключи и анонимные запросы.

| Имя | Пример | По умолчанию | Обязательно | Описание |
| :---: | :---: | :---: | :---: | :---: |
| issuer | "https://api.bencher.example.com" | --- | Да | Публичный origin этого API-сервера, по которому приложения находят его эндпоинты OAuth: `https`, или `http` только для loopback-хоста, например `localhost`. Это должен быть origin без пути, иначе сервер не запустится. **ВНИМАНИЕ** Изменение этого значения отключает все приложения. |
| resources | `["https://mcp.bencher.example.com/mcp", "https://api.bencher.example.com/mcp"]` | [`<issuer>/mcp`] | Нет | URL эндпоинта MCP этого сервера, в которые входят приложения, канонический первым: `https`, или `http` только для loopback-хоста. Приложение, которое не указывает ни один, получает первый. Удаление URL отключает приложения, вошедшие через него. |
| clients | [\{ ... \}] | --- | Нет | Единственные приложения, которым разрешено входить. Перечисленные приложения помечаются как проверенные на странице согласия. Если не указано, войти может попросить любое приложение, если API-сервер может получить действительный документ метаданных клиента по его идентификатору клиента. |
| clients.id | "https://app.example.com/oauth/client.json" | --- | Да | Идентификатор клиента приложения: `https` URL его документа метаданных клиента. |
| clients.metadata | \{ ... \} | --- | Нет | Документ метаданных клиента приложения, который используется вместо получения его по `id`, например на сервере без доступа к интернету. Это должен быть действительный документ метаданных клиента, чей `client_id` совпадает с `id`, иначе сервер не запустится. |
| signing_key | `"-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n"` | --- | Нет | Закрытый ключ RSA длиной не менее 2048 бит в формате PEM (PKCS #1 или PKCS #8), которым подписываются ID-токены. Он включает OpenID Connect: области доступа `openid`, `email` и `profile`, ID-токены, а также эндпоинты UserInfo, JWKS и discovery. Если не указан, OpenID Connect выключен. Если ключ недействителен, сервер не запустится. **ОН ДОЛЖЕН БЫТЬ ОЧЕНЬ БЕЗОПАСНЫМ!** При записи в журнал он будет выглядеть как `************`. |

Строка JSON не может содержать перевод строки, поэтому записывайте каждый перевод строки в `signing_key` как `\n`.
Например, сгенерируйте ключ и выведите его как строку JSON, не записывая в файл:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 | jq -Rs .
```

Чтобы сменить ключ подписи, замените его. Это не отключает ни одно приложение.

API-сервер обслуживает свои эндпоинты и метаданные OAuth в корне `issuer`.
Если обратный прокси обслуживает API-сервер под префиксом пути, например `https://bencher.example.com/api`,
укажите в `issuer` origin (`https://bencher.example.com`) и перечислите полный URL эндпоинта MCP в `resources` (`https://bencher.example.com/api/mcp`).
Тогда прокси должен направлять запросы к `/oauth/`, `/.well-known/oauth-authorization-server` и `/.well-known/openid-configuration` в корне origin на те же пути API-сервера,
а запросы к пути метаданных каждого ресурса, здесь `/.well-known/oauth-protected-resource/api/mcp`, на `/.well-known/oauth-protected-resource/mcp` API-сервера.
Если ресурсов больше одного, прокси также должен передавать заголовок `Host` без изменений, поскольку по нему API-сервер выбирает, какой ресурс объявить.
