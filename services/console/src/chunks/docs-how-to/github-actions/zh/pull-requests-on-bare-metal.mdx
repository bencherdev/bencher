## 裸机上的 Pull Requests

GitHub Actions 提供自托管运行器，
但它们要求您使用其噪声较大的 [GitHub Actions Runner][github actions runner] 二进制文件。
[Bencher Bare Metal][bare metal] 使用专门打造的低噪声基准测试运行器，
在专用的裸机硬件集群上运行基准测试。
此外，Bencher Bare Metal 支持来自 Fork 的 PR，
而 GitHub Actions Runner 不支持。

一旦您切换到 Bencher Bare Metal，
您就不会希望在等待 Bencher 时还有一个 GitHub Actions 作业在运行。
为了解决这个问题，工作流提交 Bencher Bare Metal 的 Job 后即退出。
Job 完成时，Bencher 自己完成 GitHub 检查，
并将结果作为评论发布到拉取请求上。

以下示例适用于**同一**仓库内的分支。
将此模式与上面的[来自 Fork 的拉取请求][pull requests from forks]工作流结合使用，
即可为 Fork PR 提供裸机基准测试。

首先，将仓库与项目关联一次：

1. 在 Bencher 控制台中，打开项目的 `Settings`，然后打开 `Connections`。
2. 在 GitHub 卡片上，点击 `Link repository`。
   GitHub 会将您带回 `Connections`，卡片会列出您可以推送的每个仓库。
3. 点击仓库旁边的 `Link`。
   如果仓库不在列表中，请点击 `Install on GitHub`，并授予应用对该仓库的访问权限。
   如果仓库显示 `Approval required`，请点击 `Approve on GitHub` 并批准应用的新权限，然后重新打开 `Connections` 并点击 `Link repository`。

关联仓库需要项目的 Maintainer 角色（组织的 Leader 和服务器管理员拥有该角色）以及对该仓库的推送权限。
Bencher 的 GitHub App 需要对仓库的检查和拉取请求的读写权限，以及对仓库内容的读取权限，因此它无法向仓库推送。
Bencher 会为关联的仓库创建一个令牌，并使用该令牌发布 GitHub 检查和拉取请求评论。
如果 GitHub 卡片显示 `Disconnected`，请点击 `Install on GitHub` 并重新授予应用对该仓库的访问权限，或者解除应用安装的暂停，关联随即恢复。
对于 Bencher Self-Hosted，服务器需要[自己的 GitHub App][github app]以及 `v0.6.18` 或更高版本。

> 🐰 任何拥有项目 API 密钥的人，都可以让 Bencher 在关联仓库中的任意提交或拉取请求上
> 发布 GitHub 检查或拉取请求评论。
> 请像对待其他任何机密一样，对 `BENCHER_API_KEY` 保密。

1. 创建一个 GitHub Actions `workflow` 文件。
   （例如：`.github/workflows/pr_bare_metal_benchmarks.yml`）
2. 为此工作流程命名。
   （例如：`name: Bare Metal PR Benchmarks with Bencher`）
3. 像上面的[拉取请求][pull requests]一样，在 `pull_request` 事件上运行。
   （例如：`on: pull_request: types: [opened, reopened, edited, synchronize]`）
4. 创建一个 GitHub Actions `job`。
   （例如：`jobs: submit_pr_benchmarks`）
5. 如果且仅当拉取请求来自同一仓库时，在 `pull_request` 事件上运行。
   ⚠️ 不要删除此行！
   处理 Fork PR 请参见上面的[来自 Fork 的拉取请求][pull requests from forks]。
   （例如：`if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`）
6. 将 [`GITHUB_TOKEN` 的权限][github token permissions] 设置为 `read` 以用于 `contents`。
   Bencher 会发布 GitHub 检查和评论，因此工作流不需要写入权限。
   （例如：`permissions: contents: read`）
7. 设置运行作业的机器类型。
   它只提交 Job，因此一台小型机器就足够了。
   （例如：`runs-on: ubuntu-latest`）
8. 检出 PR 分支的源代码。
   （例如：`uses: actions/checkout@v6`）
9. 使用 [GitHub Action][bencher cli github action] 安装 Bencher CLI。
   （例如：`uses: bencherdev/bencher@main`）
10. 使用 <code><a href="/zh/docs/explanation/bencher-run/">bencher run</a></code> CLI 子命令提交您的拉取请求分支基准测试。
    查看 [`bencher run` CLI 子命令][bencher run] 以获取完整概览。
    （例如：`bencher run`）
11. 将 `--project` 选项设置为项目 slug。
    查看 [`--project` 文档][project option] 以获取详细信息。
    （例如：`--project project-abc4567-wxyz123456789`）
12. 将 `--key` 选项设置为 `BENCHER_API_KEY` **仓库**密钥。
    查看 [`--key` 文档][key option] 以获取详细信息。
    （例如：`--key '${{ secrets.BENCHER_API_KEY }}'`）
13. 使用 [GitHub Actions `GITHUB_HEAD_REF` 默认环境变量][github default environment variables] 设置 `--branch` 选项为 PR 分支名称。
    查看 [`--branch` 文档][branch option] 以获取完整概览。
    （例如：`--branch "$GITHUB_HEAD_REF"`）
14. 像上面的[拉取请求][pull requests]一样，将 `--hash` 选项设置为 PR 分支的 `git` hash。
    查看 [`--hash` 文档][hash option] 以获取完整概览。
    （例如：`--hash '${{ github.event.pull_request.head.sha }}'`）
15. 像上面的[拉取请求][pull requests]一样，设置 PR 分支的起点。
    查看 [`--start-point` 文档][start point] 以获取完整概览。
    （例如：`--start-point "$GITHUB_BASE_REF"`）
16. 将 `--adapter` 选项设置为由 <code><a href="/zh/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code> 生成的 [Bencher Metric Format JSON (`json`)][bmf]。
    查看 [基准测试工具适配器][adapter json] 以获取完整概览。
    （例如：`--adapter json`）
17. 将 `--image` 选项设置为您的裸机镜像。
    查看 [`--image` 文档][image option] 以获取完整概览。
    （例如：`--image project-abc4567-wxyz123456789:latest`）
18. 设置 `--detach` 标志，以便在 Job 提交后立即退出。
    查看 [`--detach` 文档][detach option] 以获取详细信息。
    （例如：`--detach`）
19. 将 `--github-actions` 选项设置为 [GitHub Actions `GITHUB_TOKEN` 环境变量][github token]。
    使用 `--detach` 时，`bencher run` 会将 GitHub Actions 事件中的仓库、头提交和拉取请求编号随 Job 一起发送，并且不会使用该令牌向 GitHub 发出任何请求。
    查看 [`--github-actions` 文档][github actions option] 以获取详细信息。
    （例如：`--github-actions '${{ secrets.GITHUB_TOKEN }}'`）
20. 指定在镜像中运行的基准测试命令。
    如果镜像有入口点，该命令会传给该入口点（参见 [`--entrypoint` 选项][entrypoint option]）。
    查看 [基准测试命令][command argument] 以获取完整概览。
    （例如：`bencher mock`）

如果 Bencher 无法发布结果，它会拒绝提交 Job：
服务器没有 GitHub App、项目未被认领，或者项目没有与工作流所在仓库对应的已连接关联仓库。
提交之后，Bencher 会在头提交上启动 GitHub 检查。
Job 完成时，Bencher 会按照 [`--github-actions` 选项][github actions option] 的说明，先完成 GitHub 检查，然后写入拉取请求评论。
如果报告有警报或 Job 失败，GitHub 检查将以失败结束，
因此不需要 [`--error-on-alert` 标志][alert err]，而且它与 `--detach` 冲突。
决定结果如何发布的选项，例如 `--ci-only-on-alert` 和 `--ci-id`，放在同一个命令中，Bencher 会将它们与 Job 一起保存。

GitHub 检查属于 Bencher 的 GitHub App，而不属于 GitHub Actions。
如果分支保护规则或规则集 [要求该 GitHub 检查][github required status checks]，请将 Bencher 的 GitHub App 设置为它的来源。
否则，GitHub 会一直等待一个永远不会到来的来自 GitHub Actions 的 GitHub 检查。

如果 Bencher 的 GitHub App 的安装尚未批准其新权限，Bencher 将无法发布结果。
Job 会记录该失败以及批准权限的链接，如果 `bencher run` 在退出前看到该失败，它会打印该链接。
权限获得批准后，下一次运行就会发布其结果。

没有拉取请求的 Job，例如来自 `push` 事件的 Job，会得到 GitHub 检查，但不会得到评论。
提交已不再是拉取请求头提交的 Job 也是如此。
如果该拉取请求还有项目的不带 `--detach` 的运行，这些运行会从 GitHub Actions 机器人获得第二条评论。
