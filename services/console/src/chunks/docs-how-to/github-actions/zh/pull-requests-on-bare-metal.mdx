## 裸机上的 Pull Requests

GitHub Actions 提供自托管运行器，
但它们要求您使用其噪声较大的 [GitHub Actions Runner][github actions runner] 二进制文件。
[Bencher Bare Metal][bare metal] 使用专门打造的低噪声基准测试运行器，
在专用的裸机硬件集群上运行基准测试。
此外，Bencher Bare Metal 支持来自 Fork 的 PR，
而 GitHub Actions Runner 不支持。

一旦您切换到 Bencher Bare Metal，
您就不会希望在等待 Bencher 时还有一个 GitHub Actions 作业在运行。
为了解决这个问题，Bencher 使用拆分的工作流，
使 GitHub Actions 能够异步等待 Bencher Bare Metal 的 Job。

以下示例适用于**同一**仓库内的分支。
将此模式与上面的[来自 Fork 的拉取请求][pull requests from forks]工作流结合使用，
即可为 Fork PR 提供裸机基准测试。

<PullRequestsOnBareMetalSubmitCode />

1. 创建第一个 GitHub Actions `workflow` 文件。
   （例如：`.github/workflows/pr_bare_metal_benchmarks.yml`）
2. 为此工作流程命名。
   （例如：`name: Bare Metal PR Benchmarks with Bencher`）
3. 像上面的[拉取请求][pull requests]一样，在 `pull_request` 事件上运行。
   （例如：`on: pull_request: types: [opened, reopened, edited, synchronize]`）
4. 创建一个 GitHub Actions `job`。
   （例如：`jobs: submit_pr_benchmarks`）
5. 如果且仅当拉取请求来自同一仓库时，在 `pull_request` 事件上运行。
   ⚠️ 不要删除此行！
   处理 Fork PR 请参见上面的[来自 Fork 的拉取请求][pull requests from forks]。
   （例如：`if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`）
6. 将 [`GITHUB_TOKEN` 的权限][github token permissions] 设置为 `write` 以用于 `checks`。
   第一个工作流会启动 GitHub 检查，但不会发布评论。
   （例如：`permissions: checks: write`）
7. 设置运行作业的机器类型。
   它只提交 Job，因此一台小型机器就足够了。
   （例如：`runs-on: ubuntu-latest`）
8. 检出 PR 分支的源代码。
   （例如：`uses: actions/checkout@v6`）
9. 使用 [GitHub Action][bencher cli github action] 安装 Bencher CLI。
   （例如：`uses: bencherdev/bencher@main`）
10. 使用 <code><a href="/zh/docs/explanation/bencher-run/">bencher run</a></code> CLI 子命令提交您的拉取请求分支基准测试。
    查看 [`bencher run` CLI 子命令][bencher run] 以获取完整概览。
    （例如：`bencher run`）
11. 将 `--project` 选项设置为项目 slug。
    查看 [`--project` 文档][project option] 以获取详细信息。
    （例如：`--project project-abc4567-wxyz123456789`）
12. 将 `--key` 选项设置为 `BENCHER_API_KEY` **仓库**密钥。
    查看 [`--key` 文档][key option] 以获取详细信息。
    （例如：`--key '${{ secrets.BENCHER_API_KEY }}'`）
13. 使用 [GitHub Actions `GITHUB_HEAD_REF` 默认环境变量][github default environment variables] 设置 `--branch` 选项为 PR 分支名称。
    查看 [`--branch` 文档][branch option] 以获取完整概览。
    （例如：`--branch "$GITHUB_HEAD_REF"`）
14. 像上面的[拉取请求][pull requests]一样，设置 PR 分支的起点。
    查看 [`--start-point` 文档][start point] 以获取完整概览。
    （例如：`--start-point "$GITHUB_BASE_REF"`）
15. 将 `--adapter` 选项设置为由 <code><a href="/zh/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code> 生成的 [Bencher Metric Format JSON (`json`)][bmf]。
    查看 [基准测试工具适配器][adapter json] 以获取完整概览。
    （例如：`--adapter json`）
16. 将 `--image` 选项设置为您的裸机镜像。
    查看 [`--image` 文档][image option] 以获取完整概览。
    （例如：`--image project-abc4567-wxyz123456789:latest`）
17. 设置 `--detach` 标志，以便在 Job 提交后立即退出。
    查看 [`--detach` 文档][detach option] 以获取详细信息。
    （例如：`--detach`）
18. 使用 [GitHub Actions `GITHUB_TOKEN` 环境变量][github token] 将 `--github-actions` 选项设置为 GitHub API 身份验证令牌，以启动 GitHub 检查。
    查看 [`--github-actions` 文档][github actions option] 以获取详细信息。
    （例如：`--github-actions '${{ secrets.GITHUB_TOKEN }}'`）
19. 将 `--ci-callback-token` 选项设置为 `BENCHER_CALLBACK_TOKEN` **仓库**密钥，
    以便 Bencher 能在 Job 完成时发送 `repository_dispatch` 事件。
    查看 [`--ci-callback-token` 文档][ci callback token option] 以获取详细信息。
    （例如：`--ci-callback-token '${{ secrets.BENCHER_CALLBACK_TOKEN }}'`）
20. 指定在镜像中运行的基准测试命令。
    如果镜像有入口点，该命令会传给该入口点（参见 [`--entrypoint` 选项][entrypoint option]）。
    查看 [基准测试命令][command argument] 以获取完整概览。
    （例如：`bencher mock`）

<PullRequestsOnBareMetalAttachCode />

1. 在默认分支上创建第二个 GitHub Actions `workflow` 文件。
   GitHub 只会从默认分支运行 `repository_dispatch` 工作流，
   因此在该文件出现在默认分支之前，第一个工作流启动的 GitHub 检查会一直保持进行中。
   （例如：`.github/workflows/pr_bare_metal_benchmarks_attach.yml`）
2. 为此工作流程命名。
   （例如：`name: Attach Bare Metal PR Benchmarks with Bencher`）
3. 在类型为 `bencher_run` 的 `repository_dispatch` 事件上运行。
   查看 [GitHub Actions `on` 文档][github actions on] 和 [GitHub Actions `repository_dispatch` 文档][github repository_dispatch] 以获取完整概览。
   （例如：`on: repository_dispatch: types: [bencher_run]`）
4. 创建一个 GitHub Actions `job`。
   （例如：`jobs: attach_pr_benchmarks`）
5. 将 [`GITHUB_TOKEN` 的权限][github token permissions] 设置为 `write` 以用于 `checks` 和 `pull-requests`。
   （例如：`permissions: checks: write pull-requests: write`）
6. 设置运行作业的机器类型。
   Job 已经完成，因此该作业只发布结果。
   （例如：`runs-on: ubuntu-latest`）
7. 使用 [GitHub Action][bencher cli github action] 安装 Bencher CLI。
   不需要检出代码。
   （例如：`uses: bencherdev/bencher@main`）
8. 按照 GitHub 关于脚本注入的指导，通过[中间环境变量][github intermediate environment variable]传递事件中的 Job UUID，切勿直接写在 `run:` 中。
   （例如：`env: JOB_UUID: ${{ github.event.client_payload.bencher.job }}`）
9. 使用 <code><a href="/zh/docs/explanation/bencher-run/">bencher run</a></code> CLI 子命令连接到该 Job。
   查看 [`bencher run` CLI 子命令][bencher run] 以获取完整概览。
   （例如：`bencher run`）
10. 将 `--project` 选项设置为项目 slug。
    如果仓库有多个项目，请以同样的方式通过环境变量传递 `github.event.client_payload.bencher.project`，并用引号括起来（例如：`--project "$PROJECT_SLUG"`）。
    查看 [`--project` 文档][project option] 以获取详细信息。
    （例如：`--project project-abc4567-wxyz123456789`）
11. 将 `--key` 选项设置为 `BENCHER_API_KEY` **仓库**密钥。
    查看 [`--key` 文档][key option] 以获取详细信息。
    （例如：`--key '${{ secrets.BENCHER_API_KEY }}'`）
12. 将 `--job` 选项设置为加上引号的 Job UUID。
    查看 [`--job` 文档][job option] 以获取完整概览。
    （例如：`--job "$JOB_UUID"`）
13. 设置 `--error-on-alert` 标志，以便在生成警报时使命令失败。
    事件只携带数据，因此决定结果如何发布的选项，例如 `--ci-only-on-alert` 和 `--ci-public-links`，也放在这里，即第二个工作流中。
    查看 [`--error-on-alert` 文档][alert err] 以获取完整概览。
    （例如：`--error-on-alert`）
14. 使用 [GitHub Actions `GITHUB_TOKEN` 环境变量][github token] 将 `--github-actions` 选项设置为 GitHub API 身份验证令牌，以将结果发布为 GitHub 检查和拉取请求评论。
    在这里显式指定的 `--ci-number` 或 `--ci-id` 优先于事件。
    查看 [`--github-actions` 文档][github actions option] 以获取详细信息。
    （例如：`--github-actions '${{ secrets.GITHUB_TOKEN }}'`）
