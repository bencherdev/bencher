### `--ci-id <ID>`

<br />

Optional: Benutzerdefinierte ID zum Posten von Ergebnissen an CI.
Alle Jobs eines Projekts in einem Pull Request teilen sich einen Kommentar, mit einer Berichtszeile für jeden Job.
Mit einer ID ist die Beschriftung der Zeile ihre Nummer und die ID (z.B.: `2 (microbench)`).
Solange der Bericht des Jobs noch nicht existiert, zeigt seine Zeile nur die ID und keine Nummer (z.B.: `(microbench)`), als `Pending`, solange der Job läuft, und steht nach den nummerierten Zeilen.
Ohne ID ist die Beschriftung nur die Nummer, und die Zeile erscheint, sobald der Bericht des Jobs existiert.
Standardmäßig teilen sich Jobs eine Zeile, wenn sie die gleiche Kombination von: Branch, Testbed und [Adapter](/de/docs/explanation/adapters/) haben,
zusammen mit [`--build-time`](#--build-time) und [`--file-size`](#--file-size-file), falls gesetzt.
Das Festlegen einer benutzerdefinierten ID ist nützlich, wenn Bencher auf dem gleichen Commit mehrmals für die gleiche Projekt-, Branch-, Testbed- und Adapter-Kombination ausgeführt wird,
damit jeder Lauf seine eigene Zeile erhält.
Zum Beispiel teilen sich ein `push`-Lauf und ein `pull_request`-Lauf auf demselben Branch den Head-Commit,
geben Sie daher jedem Lauf eine eigene ID, oder verwenden Sie `--github-actions` nicht für den `push`-Lauf.
Andernfalls teilen sich die Läufe eine Zeile, die nur einen von ihnen zeigt, und ein älterer Lauf schreibt nichts, sobald ein neuerer Lauf die Zeile belegt.
Die ID wird außerdem anstelle des Projektnamens im Namen der GitHub-Prüfung verwendet (d.h. `Bencher Report (<ID>)`),
sodass jeder Aufruf einen stabilen Namen erhält, der als separate erforderliche Statusprüfung verwendet werden kann.
Erforderlich: `--github-actions`
