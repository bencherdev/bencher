### `plus.registry`

Esta sección especifica la configuración de almacenamiento del registro OCI (Open Container Initiative).
Bencher puede funcionar como un registro de contenedores/artefactos compatible con OCI.

Si esta sección no está configurada, Bencher usará almacenamiento en el sistema de archivos local
en un directorio `registry` junto al archivo de base de datos.
Esto es adecuado para desarrollo y despliegues de instancia única.

Para despliegues de producción con múltiples instancias o para durabilidad,
configure almacenamiento compatible con S3.

Hay dos `scheme`s de almacenamiento:
- `file`: Almacenar artefactos OCI en el sistema de archivos local (predeterminado)
    - `path`: (Opcional) Directorio para los datos del registro. Por defecto, un directorio `registry` junto al archivo de base de datos.
- `s3`: Almacenar artefactos OCI en cualquier almacenamiento compatible con S3
    - `bucket`: Nombre del bucket
    - `path`: (Opcional) Prefijo de clave en el bucket. Las barras iniciales, finales y repetidas se eliminan, por lo que `registry`, `registry/` y `/registry` almacenan todos bajo `registry`.
    - `endpoint`: (AWS: Opcional | No AWS: Requerido) Punto final de almacenamiento
    - `region`: (Opcional) Región del bucket. Requerido para AWS. Por defecto `auto`, que es lo que esperan los almacenamientos compatibles con S3.
    - `access_key_id`: Clave de acceso S3
    - `secret_access_key`: Clave secreta de acceso S3
    - `chunk_size`: (Opcional) Tamaño de parte en bytes para las cargas de blobs, de 5 MiB a 5 GiB. Predeterminado: 16 MiB (16.777.216 bytes).
      Una carga se transmite a una carga multiparte en partes de este tamaño, y una sesión de carga conserva el tamaño de parte con el que comenzó.

Las cargas de blobs necesitan tres cosas de un almacenamiento compatible con S3: el ETag de cada parte cargada es el MD5 de esa parte, una carga multiparte completada tiene el ETag multiparte estándar, y un `UploadPartCopy` prefirmado funciona. Cloudflare R2 cumple las tres.

El servidor aborta una carga multiparte cuando falla la solicitud que la abrió, y las cargas multiparte que guardó una sesión de carga abandonada cuando limpia las cargas obsoletas. Además, establezca una regla de ciclo de vida del bucket que aborte las cargas multiparte incompletas: un fallo del servidor todavía puede dejar una carga que solo esta regla elimina.

Si anteriormente configuró un `path` que comenzaba o terminaba con una barra, mueva los objetos existentes al prefijo normalizado antes de actualizar. Un `path` de `registry/` almacenaba claves bajo `registry//<project>/...` y ahora las almacena bajo `registry/<project>/...`. Cada segmento de `path` también se codifica en porcentaje en la clave almacenada cuando contiene un carácter de control ASCII, un carácter no ASCII o uno de `\` `{` `^` `}` `%` `` ` `` `]` `"` `>` `[` `~` `<` `#` `|` `*` `?`, y un segmento que sea exactamente `.` o `..` se almacena como `%2E` o `%2E%2E`. Cualquier otro carácter, incluidos los espacios, `+`, `=`, `@` y `:`, se almacena tal cual, por lo que `team#1` se convierte en `team%231` mientras que `team+1` sigue siendo `team+1`. Los datos almacenados bajo un prefijo que ahora se codifica necesitan el mismo traslado. Antes de mover cualquier dato, liste las claves realmente almacenadas en el bucket y compárelas con el nuevo prefijo.
