## 베어 메탈에서의 Pull Requests

GitHub Actions에는 Self-Hosted 러너가 있지만, 이를 사용하려면
노이즈가 많은 [GitHub Actions Runner][github actions runner] 바이너리를 사용해야 합니다.
[Bencher Bare Metal][bare metal]은 목적에 맞게 설계된 저노이즈 벤치마크 러너를 사용하여
전용 베어 메탈 하드웨어 플릿에서 벤치마크를 실행합니다.
또한 Bencher Bare Metal은 포크에서 온 PR을 지원하지만,
GitHub Actions Runner는 지원하지 않습니다.

Bencher Bare Metal로 전환한 뒤에는,
Bencher를 기다리는 동안 GitHub Actions 작업을 계속 실행해 두고 싶지 않을 것입니다.
이를 해결하기 위해 워크플로는 Bencher Bare Metal Job을 제출하고 종료합니다.
Job이 끝나면 Bencher가 직접 GitHub Check를 완료하고
결과를 pull request의 댓글로 게시합니다.

다음 예시는 **동일한** 저장소 내의 브랜치에서 사용하기 위한 것입니다.
포크 PR에서 베어 메탈 벤치마킹을 하려면
위의 [포크에서의 Pull Requests][pull requests from forks] 워크플로와
이 패턴을 함께 사용하세요.

먼저 저장소를 프로젝트에 한 번 연결합니다.

1. Bencher Console에서 프로젝트의 `Settings`를 연 다음 `Connections`를 엽니다.
2. GitHub 카드에서 `Link repository`를 클릭합니다.
   GitHub에서 `Connections`로 돌아오면, 카드에 푸시할 수 있는 각 저장소가 나열됩니다.
3. 저장소 옆의 `Link`를 클릭합니다.
   목록에 없으면 `Install on GitHub`를 클릭하고 앱에 해당 저장소에 대한 접근 권한을 부여합니다.
   `Approval required`가 표시되면 `Approve on GitHub`를 클릭하여 앱의 새 권한을 승인한 다음, `Connections`를 다시 열고 `Link repository`를 클릭합니다.

연결하려면 프로젝트의 Maintainer 역할(조직의 Leader와 서버 관리자가 가진 역할)과 저장소에 대한 푸시 권한이 필요합니다.
Bencher의 GitHub 앱에는 저장소의 checks와 pull requests에 대한 읽기 및 쓰기 권한과 콘텐츠에 대한 읽기 권한이 필요하므로, 앱은 저장소에 푸시할 수 없습니다.
Bencher는 연결된 저장소에 대한 토큰을 만들고 그 토큰으로 GitHub Check와 pull request 댓글을 게시합니다.
GitHub 카드에 `Disconnected`가 표시되면 `Install on GitHub`를 클릭하고 앱에 저장소에 대한 접근 권한을 다시 부여하거나 앱 설치의 일시 중지를 해제하면 연결이 다시 이어집니다.
Bencher Self-Hosted의 경우 서버에 [자체 GitHub 앱][github app]과 `v0.6.18` 이상의 버전이 필요합니다.

> 🐰 프로젝트의 API 키를 가진 사람은 누구나 연결된 저장소의 어떤 커밋이나 pull request에도
> Bencher가 GitHub Check나 pull request 댓글을 게시하게 할 수 있습니다.
> `BENCHER_API_KEY`는 다른 시크릿과 마찬가지로 비밀로 유지하세요.

1. GitHub Actions `workflow` 파일을 생성합니다.
   (예: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. 이 워크플로의 이름을 지정합니다.
   (예: `name: Bare Metal PR Benchmarks with Bencher`)
3. 위의 [Pull Requests][pull requests]처럼 `pull_request` 이벤트에서 실행합니다.
   (예: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. GitHub Actions `job`을 생성합니다.
   (예: `jobs: submit_pr_benchmarks`)
5. pull request가 동일한 저장소에서 온 경우에만 `pull_request` 이벤트에서 실행합니다.
   ⚠️ 이 라인을 제거하지 마십시오!
   포크 PR 처리에 관해서는 위의 [포크에서의 Pull Requests][pull requests from forks]를 참조하세요.
   (예: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. `GITHUB_TOKEN`의 [권한을 설정][github token permissions]하여 `contents`에 `read`를 부여합니다.
   Bencher가 GitHub Check와 댓글을 게시하므로 워크플로에는 쓰기 권한이 필요하지 않습니다.
   (예: `permissions: contents: read`)
7. 작업을 실행할 머신의 유형을 설정합니다.
   Job을 제출하기만 하므로 작은 머신으로 충분합니다.
   (예: `runs-on: ubuntu-latest`)
8. PR 브랜치의 소스 코드를 체크아웃합니다.
   (예: `uses: actions/checkout@v6`)
9. [GitHub Action][bencher cli github action]을 사용하여 Bencher CLI를 설치합니다.
   (예: `uses: bencherdev/bencher@main`)
10. PR 브랜치 벤치마크를 제출하기 위해 <code><a href="/ko/docs/explanation/bencher-run/">bencher run</a></code> CLI 서브커맨드를 사용합니다.
    전체 개요는 [`bencher run` CLI 서브커맨드][bencher run]를 참조하세요.
    (예: `bencher run`)
11. `--project` 옵션을 프로젝트 슬러그로 설정합니다.
    더 많은 세부 사항은 [`--project` 문서][project option]를 참조하세요.
    (예: `--project project-abc4567-wxyz123456789`)
12. `--key` 옵션을 `BENCHER_API_KEY` **레포지토리** 시크릿으로 설정합니다.
    더 많은 세부 사항은 [`--key` 문서][key option]를 참조하세요.
    (예: `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. [GitHub Actions `GITHUB_HEAD_REF` 기본 환경 변수][github default environment variables]를 사용하여 PR 브랜치 이름을 `--branch` 옵션으로 설정합니다.
    전체 개요는 [`--branch` 문서][branch option]를 참조하세요.
    (예: `--branch "$GITHUB_HEAD_REF"`)
14. 위의 [Pull Requests][pull requests]처럼 `--hash` 옵션을 PR 브랜치의 `git` 해시로 설정합니다.
    전체 개요는 [`--hash` 문서][hash option]를 참조하세요.
    (예: `--hash '${{ github.event.pull_request.head.sha }}'`)
15. 위의 [Pull Requests][pull requests]처럼 PR 브랜치의 시작점을 설정합니다.
    전체 개요는 [`--start-point` 문서][start point]를 참조하세요.
    (예: `--start-point "$GITHUB_BASE_REF"`)
16. `--adapter` 옵션을 <code><a href="/ko/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>이 생성하는 [Bencher Metric Format JSON (`json`)][bmf]으로 설정합니다.
    전체 개요는 [벤치마크 하니스 어댑터][adapter json]를 참조하세요.
    (예: `--adapter json`)
17. `--image` 옵션을 베어 메탈 이미지로 설정합니다.
    전체 개요는 [`--image` 문서][image option]를 참조하세요.
    (예: `--image project-abc4567-wxyz123456789:latest`)
18. Job을 제출하자마자 종료하도록 `--detach` 플래그를 설정합니다.
    더 많은 세부 사항은 [`--detach` 문서][detach option]를 참조하세요.
    (예: `--detach`)
19. `--github-actions` 옵션을 [GitHub Actions `GITHUB_TOKEN` 환경 변수][github token]로 설정합니다.
    `--detach`를 사용하면 `bencher run`은 GitHub Actions 이벤트의 저장소, 헤드 커밋, pull request 번호를 Job과 함께 보내며, 토큰으로 GitHub에 요청하지 않습니다.
    더 많은 세부 사항은 [`--github-actions` 문서][github actions option]를 참조하세요.
    (예: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. 이미지 안에서 실행할 벤치마크 명령을 지정합니다.
    이미지에 엔트리포인트가 있으면 명령은 그 엔트리포인트에 전달됩니다([`--entrypoint` 옵션][entrypoint option] 참조).
    전체 개요는 [벤치마크 명령][command argument]을 참조하세요.
    (예: `bencher mock`)

Bencher가 결과를 게시할 수 없으면 Bencher는 Job 제출을 거부합니다.
즉, 서버에 GitHub 앱이 없거나, 프로젝트가 클레임되지 않았거나, 프로젝트에 워크플로의 저장소에 대한 연결된 저장소가 연결 상태로 없는 경우입니다.
제출 후 Bencher는 헤드 커밋에서 GitHub Check를 시작합니다.
Job이 끝나면 Bencher는 [`--github-actions` 옵션][github actions option]에 설명된 대로 GitHub Check를 완료한 다음 pull request 댓글을 작성합니다.
보고서에 경고가 있거나 Job이 실패하면 GitHub Check는 실패로 끝납니다.
따라서 [`--error-on-alert` 플래그][alert err]는 필요하지 않으며, `--detach`와 충돌합니다.
`--ci-only-on-alert`와 `--ci-id`처럼 결과를 게시하는 방식을 정하는 옵션은 같은 명령에 지정하며, Bencher는 이를 Job과 함께 저장합니다.

GitHub Check는 GitHub Actions가 아니라 Bencher의 GitHub 앱에 속합니다.
브랜치 보호 규칙이나 규칙 집합이 [GitHub Check를 요구하는][github required status checks] 경우, 그 소스로 Bencher의 GitHub 앱을 설정하세요.
그렇지 않으면 GitHub는 결코 오지 않을 GitHub Actions의 GitHub Check를 기다립니다.

Bencher의 GitHub 앱 설치가 새 권한을 승인하지 않았다면 Bencher는 결과를 게시할 수 없습니다.
Job은 권한 승인 링크와 함께 실패를 기록하며, `bencher run`은 종료 전에 실패를 확인하면 그 링크를 출력합니다.
권한이 승인되면 다음 실행부터 결과를 게시합니다.

`push` 이벤트에서 온 Job처럼 pull request가 없는 Job은 GitHub Check를 받고 댓글은 받지 않습니다.
커밋이 더 이상 pull request의 헤드가 아닌 Job도 마찬가지입니다.
pull request에 `--detach` 없이 실행한 프로젝트의 실행도 있다면, 그 실행에 대해 GitHub Actions 봇이 두 번째 댓글을 게시합니다.
