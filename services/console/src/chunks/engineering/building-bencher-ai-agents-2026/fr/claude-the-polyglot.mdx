## Claude le polyglotte

En 2023, j'ai décidé que je voulais que la documentation de Bencher soit disponible en 9 langues : anglais, chinois, espagnol, portugais brésilien, russe, japonais, français, allemand et coréen. Comment ai-je choisi ces neuf langues ? Ce sont les langues dans lesquelles la documentation de GitHub était disponible, alors je me suis dit que c'était une approximation suffisante. Le seul problème, c'est que je ne parle couramment que l'anglais. J'ai donc fait traduire la documentation par GPT-4. À l'époque, GPT-4 n'avait qu'une fenêtre de contexte de 8k tokens. Cela signifiait que je devais découper toutes mes pages de documentation en "chunks" de moins de 8k tokens. Ensuite, j'ai dû créer un outil CLI pour gérer la traduction, et très souvent la retraduction, des chunks après leur mise à jour.

C'était un processus très fastidieux et sujet aux erreurs. Je devais retoucher à la main les fichiers traduits parce que, même avec des instructions très explicites dans le prompt système, le modèle massacrait quand même les chemins d'import ou fourrait tout dans une couche supplémentaire de bloc Markdown, surtout en japonais, allez savoir pourquoi.

Une fois que j'ai commencé à utiliser Claude Code avec Opus 4.5, tout cela a disparu. Maintenant, l'agent s'en charge, tout simplement. La convention qui définit ce qu'est un chunk se trouve dans la base de code, et Claude la suit, tout simplement. Quand j'ai rédigé la documentation technique de Bencher Bare Metal, Claude s'est simplement occupé du découpage en chunks et de l'orchestration des traductions. Même si la taille du contexte est désormais largement suffisante pour gérer une page entière, j'aime avoir les chunks. Ils permettent de garder les changements isolés, de sorte que seules les sections pertinentes d'une page sont retraduites lors d'une révision.
