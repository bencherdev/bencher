## Pull Requests auf dedizierter Hardware

GitHub Actions bietet selbstgehostete Runner, doch dafür müssen Sie
deren verrauschtes [GitHub Actions Runner][github actions runner]-Binary verwenden.
[Bencher Bare Metal][bare metal] führt Benchmarks auf einer dedizierten Flotte von Bare-Metal-Hardware
mit einem eigens dafür entwickelten, rauscharmen Benchmark-Runner aus.
Außerdem unterstützt Bencher Bare Metal PRs aus Forks,
während der GitHub Actions Runner das nicht tut.

Sobald Sie auf Bencher Bare Metal umgestiegen sind,
möchten Sie keinen GitHub Actions Job laufen lassen, während er auf Bencher wartet.
Um das zu lösen, reicht der Workflow den Job von Bencher Bare Metal ein und beendet sich.
Wenn der Job beendet ist, schließt Bencher selbst die GitHub-Prüfung ab
und veröffentlicht die Ergebnisse als Kommentar im Pull Request.

Das folgende Beispiel ist für Branches innerhalb **desselben** Repositorys gedacht.
Kombinieren Sie dieses Muster mit
dem obigen Workflow [Pull Requests aus Forks][pull requests from forks],
um Benchmarking auf dedizierter Hardware für Fork-PRs zu erhalten.

Verknüpfen Sie zuerst einmalig das Repository mit dem Projekt:

1. Öffnen Sie in der Bencher Console die `Settings` des Projekts und dann `Connections`.
2. Klicken Sie auf der GitHub-Karte auf `Link repository`.
   GitHub bringt Sie zurück zu `Connections`, wo die Karte jedes Repository auflistet, in das Sie pushen können.
3. Klicken Sie neben dem Repository auf `Link`.
   Wenn es nicht aufgeführt ist, klicken Sie auf `Install on GitHub` und geben Sie der App Zugriff darauf.
   Wenn `Approval required` angezeigt wird, klicken Sie auf `Approve on GitHub`, genehmigen Sie die neuen Berechtigungen der App,
   öffnen Sie dann erneut `Connections` und klicken Sie auf `Link repository`.

Zum Verknüpfen benötigen Sie die Rolle Maintainer im Projekt, die Leader der Organisation und Server-Administratoren innehaben, und Push-Zugriff auf das Repository.
Die GitHub App von Bencher benötigt Lese- und Schreibzugriff auf die Checks und Pull Requests des Repositorys
und Lesezugriff auf seine Inhalte, sie kann also nicht in das Repository pushen.
Bencher erstellt ein Token für das verknüpfte Repository
und veröffentlicht damit die GitHub-Prüfung und den Kommentar im Pull Request.
Wenn die GitHub-Karte `Disconnected` anzeigt, klicken Sie auf `Install on GitHub` und geben Sie der App erneut Zugriff auf das Repository
oder heben Sie die Sperrung ihrer Installation auf, dann wird die Verknüpfung wiederhergestellt.
Für Bencher Self-Hosted benötigt der Server [eine eigene GitHub App][github app] und Version `v0.6.18` oder neuer.

> 🐰 Jeder mit dem API-Schlüssel des Projekts kann Bencher eine GitHub-Prüfung oder einen Kommentar im Pull Request
> im verknüpften Repository veröffentlichen lassen, für jeden Commit und jeden Pull Request darin.
> Halten Sie den `BENCHER_API_KEY` geheim wie jedes andere Geheimnis.

1. Erstellen Sie eine GitHub Actions `workflow`-Datei.
   (z.B.: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Benennen Sie diesen Workflow.
   (z.B.: `name: Bare Metal PR Benchmarks with Bencher`)
3. Ausführung bei `pull_request`-Ereignissen, wie oben unter [Pull Requests][pull requests].
   (z.B.: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. Erstellen Sie einen GitHub Actions `job`.
   (z.B.: `jobs: submit_pr_benchmarks`)
5. Laufen Sie bei `pull_request`-Ereignissen, wenn und nur wenn der Pull Request aus demselben Repository stammt.
   ⚠️ ENTFERNEN SIE NICHT DIESE ZEILE!
   Für die Handhabung von Fork PRs siehe oben [Pull Requests aus Forks][pull requests from forks].
   (z.B.: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. Legen Sie [die Berechtigungen für das `GITHUB_TOKEN`][github token permissions] auf `read` für `contents` fest.
   Bencher veröffentlicht die GitHub-Prüfung und den Kommentar, daher benötigt der Workflow keinen Schreibzugriff.
   (z.B.: `permissions: contents: read`)
7. Legen Sie die Art der Maschine fest, auf der der Job läuft.
   Er reicht nur den Job ein, daher genügt eine kleine Maschine.
   (z.B.: `runs-on: ubuntu-latest`)
8. Checken Sie den Quellcode des PR-Branches aus.
   (z.B.: `uses: actions/checkout@v6`)
9. Installieren Sie die Bencher CLI mithilfe [der GitHub Action][bencher cli github action].
   (z.B.: `uses: bencherdev/bencher@main`)
10. Verwenden Sie den <code><a href="/de/docs/explanation/bencher-run/">bencher run</a></code> CLI-Unterbefehl, um Ihre Pull Request-Branch-Benchmarks einzureichen.
    Siehe den [`bencher run` CLI-Unterbefehl][bencher run] für einen vollständigen Überblick.
    (z.B.: `bencher run`)
11. Setzen Sie die `--project`-Option auf das Projekt-Slug.
    Siehe [die `--project` Dokumentation][project option] für weitere Details.
    (z.B.: `--project project-abc4567-wxyz123456789`)
12. Setzen Sie die `--key`-Option auf das **Repository**-Geheimnis `BENCHER_API_KEY`.
    Siehe [die `--key` Dokumentation][key option] für weitere Details.
    (z.B.: `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. Setzen Sie die `--branch`-Option auf den PR-Branch-Namen unter Verwendung [der GitHub Actions `GITHUB_HEAD_REF` Standard-Umgebungsvariable][github default environment variables].
    Siehe [die `--branch` Dokumentation][branch option] für einen vollständigen Überblick.
    (z.B.: `--branch "$GITHUB_HEAD_REF"`)
14. Setzen Sie die `--hash`-Option auf den `git`-Hash des PR-Branches, wie oben unter [Pull Requests][pull requests].
    Siehe [die `--hash` Dokumentation][hash option] für einen vollständigen Überblick.
    (z.B.: `--hash '${{ github.event.pull_request.head.sha }}'`)
15. Setzen Sie den Startpunkt für den PR-Branch, wie oben unter [Pull Requests][pull requests].
    Siehe [die `--start-point` Dokumentation][start point] für einen vollständigen Überblick.
    (z.B.: `--start-point "$GITHUB_BASE_REF"`)
16. Setzen Sie die `--adapter`-Option auf [Bencher Metric Format JSON (`json`)][bmf], das von <code><a href="/de/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code> generiert wird.
    Siehe [Benchmark-Harness-Adapter][adapter json] für einen vollständigen Überblick.
    (z.B.: `--adapter json`)
17. Setzen Sie die `--image`-Option auf Ihr Image für dedizierte Hardware.
    Siehe [die `--image` Dokumentation][image option] für einen vollständigen Überblick.
    (z.B.: `--image project-abc4567-wxyz123456789:latest`)
18. Setzen Sie das `--detach` Flag, um sich zu beenden, sobald der Job eingereicht ist.
    Siehe [die `--detach` Dokumentation][detach option] für weitere Details.
    (z.B.: `--detach`)
19. Setzen Sie die `--github-actions`-Option auf die [GitHub Actions `GITHUB_TOKEN` Umgebungsvariable][github token].
    Mit `--detach` sendet `bencher run` das Repository, den Head-Commit und die Nummer des Pull Requests
    aus dem GitHub Actions Ereignis mit dem Job und stellt mit dem Token keine Anfrage an GitHub.
    Siehe [die `--github-actions` Dokumentation][github actions option] für mehr Details.
    (z.B.: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. Geben Sie den Benchmark-Befehl an, der im Image ausgeführt wird.
    Der Befehl wird an den Entrypoint des Images übergeben, falls es einen hat (siehe [die Option `--entrypoint`][entrypoint option]).
    Siehe [Benchmark Befehl][command argument] für einen vollständigen Überblick.
    (z.B.: `bencher mock`)

Bencher lehnt das Einreichen des Jobs ab, wenn es die Ergebnisse nicht veröffentlichen kann:
wenn der Server keine GitHub App hat, das Projekt nicht beansprucht ist
oder das Projekt kein verbundenes verknüpftes Repository für das Repository des Workflows hat.
Nach dem Einreichen startet Bencher die GitHub-Prüfung auf dem Head-Commit.
Wenn der Job beendet ist, schließt Bencher die GitHub-Prüfung ab und schreibt dann den Kommentar im Pull Request,
wie es [die `--github-actions`-Option][github actions option] beschreibt.
Die GitHub-Prüfung schlägt fehl, wenn der Bericht einen Alarm hat oder der Job fehlschlägt,
daher wird [das `--error-on-alert` Flag][alert err] nicht benötigt, und es steht im Konflikt mit `--detach`.
Optionen, die festlegen, wie die Ergebnisse veröffentlicht werden, wie `--ci-only-on-alert` und `--ci-id`, gehören in denselben Befehl,
und Bencher speichert sie mit dem Job.

Die GitHub-Prüfung gehört zur GitHub App von Bencher, nicht zu GitHub Actions.
Wenn eine Branch-Schutzregel oder ein Regelsatz [die GitHub-Prüfung erfordert][github required status checks],
legen Sie die GitHub App von Bencher als ihre Quelle fest.
Andernfalls wartet GitHub auf eine GitHub-Prüfung von GitHub Actions, die nie kommt.

Wenn die Installation der GitHub App von Bencher ihre neuen Berechtigungen nicht genehmigt hat, kann Bencher die Ergebnisse nicht veröffentlichen.
Der Job speichert den Fehler mit einem Link, um sie zu genehmigen,
und `bencher run` gibt den Link aus, wenn es den Fehler sieht, bevor es sich beendet.
Sobald die Berechtigungen genehmigt sind, veröffentlicht der nächste Lauf seine Ergebnisse.

Ein Job ohne Pull Request, etwa aus einem `push`-Ereignis, erhält eine GitHub-Prüfung und keinen Kommentar.
Das gilt auch für einen Job, dessen Commit nicht mehr der Head des Pull Requests ist.
Wenn der Pull Request auch Läufe des Projekts ohne `--detach` hat,
erhält er für diese einen zweiten Kommentar, vom GitHub Actions Bot.
