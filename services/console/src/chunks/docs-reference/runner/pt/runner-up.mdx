## `runner up`

Inicia o runner, fazendo polling e executando Jobs de benchmark.
Este é o comando de longa duração usado para operar um [Self-Hosted Runner][self hosted runners].
O runner abre uma única [conexão WebSocket][runner protocol] ao servidor de API,
reivindica Jobs que correspondam às suas Specs, os executa e reporta os resultados de volta.
O runner escreve seu log no stderr como JSON, um objeto por linha, e registra a saída de um Job apenas como contagens de bytes.

```
runner up [OPTIONS]
```

### Opções

### `--host <HOST>`

O servidor de API Bencher ao qual se conectar.
Por padrão, `https://api.bencher.dev` é usado.
Também pode ser definido com a variável de ambiente `BENCHER_HOST`.

### `--runner <RUNNER>`

O UUID ou slug do Runner sob o qual operar.
Também pode ser definido com a variável de ambiente `BENCHER_RUNNER`.

### `--key <KEY>`

A chave de autenticação do Runner (`bencher_runner_...`)
retornada quando o [Runner foi criado][create a runner].
Também pode ser definida com a variável de ambiente `BENCHER_RUNNER_KEY`.

### `--poll-timeout <POLL_TIMEOUT>`

O timeout de long-poll em segundos enquanto aguarda um Job, entre `1` e `900`.
Por padrão, `55` é usado.

### `--state-dir <STATE_DIR>`

O diretório de estado persistente do Runner.
Deve ser um caminho absoluto.
A jail que confina o sandbox é criada sob este diretório,
e as jails deixadas por um encerramento não limpo são removidas dele antes de cada Job com sandbox.
Cada jail contém um sistema de arquivos raiz completo do convidado e uma cópia do binário da microVM,
e um Runner executa os seus Jobs um de cada vez,
portanto este diretório precisa de capacidade real para uma jail.
Um host executa um único Runner por vez, seja qual for o seu diretório de estado:
um Runner iniciado como `root` mantém o bloqueio `/run/bencher/runner.lock` enquanto está em execução,
e um segundo iniciado como `root` encerra imediatamente com um erro que nomeia esse bloqueio; um Runner que não é `root` não consegue abrir o bloqueio e é executado sem ele.
Ao iniciar, e de novo antes de cada Job com sandbox, um Runner iniciado como `root` encerra qualquer processo ainda em execução em um cgroup sob `/sys/fs/cgroup/bencher`, como a sandbox de um Runner encerrado no meio de um Job, seja qual for o diretório de estado desse Runner.
Um sistema de arquivos dedicado ou uma montagem `tmpfs` é suportado e recomendado:
mantém essa carga de escrita fora do disco do sistema,
e um sistema de arquivos recém-criado é aceito mesmo que venha com um diretório `lost+found`.
O sistema de arquivos não pode estar montado com `nodev` ou `noexec`, como `/tmp`, `/dev/shm` e `/run` costumam estar, então monte para ele um `tmpfs` sem essas opções.
O próprio diretório de estado pode ser um link simbólico criado pelo root para um sistema de arquivos assim,
como `/var/lib/bencher-runner` apontando para um disco dedicado.
O link só é seguido quando o diretório que o contém só pode ser escrito pelo root,
ele aponta diretamente para o seu destino final,
e esse destino já existe em um caminho gravável apenas pelo root;
um link cujo destino ainda não existe é recusado, então crie o destino primeiro.
Por padrão, `/var/lib/bencher-runner` é usado.
Também pode ser definido com a variável de ambiente `BENCHER_STATE_DIR`.

### `--jail-uid <JAIL_UID>`

O ID de usuário sem privilégios para o qual o processo do sandbox muda.
Por padrão, `61016` é usado.
Não pode ser `0`.
Um processo no host que seja dono desse ID de usuário pode enviar sinais ao sandbox,
portanto defina um ID que o host não destine a mais nada.
Também pode ser definido com a variável de ambiente `BENCHER_JAIL_UID`.

### `--jail-gid <JAIL_GID>`

O ID de grupo sem privilégios para o qual o processo do sandbox muda.
Por padrão, `61016` é usado.
Não pode ser `0`.
Também pode ser definido com a variável de ambiente `BENCHER_JAIL_GID`.

### `--danger-allow-no-sandbox`

Permite executar Jobs sem um [Sandbox][sandbox].
Sem essa flag, um Job cuja Spec não tem Sandbox é rejeitado em tempo de execução.
Jobs sem sandbox rodam diretamente no host, então habilite isso apenas para cargas de trabalho confiáveis.
Também pode ser definida com a variável de ambiente `BENCHER_DANGER_ALLOW_NO_SANDBOX`.

### `--sandbox-log-level <SANDBOX_LOG_LEVEL>`

O nível de log para o processo do sandbox.
Por padrão, `warning` é usado.

### `--no-raid-pause`

Continuar aceitando Jobs enquanto um array RAID md do host faz ressincronização, recuperação, verificação, reparo ou remodelação.
Por padrão, o Runner verifica seus arrays md antes de pedir cada Job,
e enquanto algum deles executa uma dessas operações ele pausa: não aceita nenhum Job novo até a sincronização terminar,
e nunca interrompe um Job que já está em execução.
Um Runner pausado continua conectado e continua se atualizando.

### `--no-auto-update`

Desabilita as atualizações automáticas do servidor.
Por padrão, o runner se atualiza entre os Jobs quando o servidor oferece uma nova versão.
Também pode ser definida com a variável de ambiente `BENCHER_NO_AUTO_UPDATE`.

### `--update-channel <UPDATE_CHANNEL>`

O canal de atualização para as atualizações automáticas, `stable` ou `canary`.
Por padrão, `stable` é usado.
O canal `stable` atualiza para releases versionadas.
O canal `canary` acompanha o build canary contínuo,
que é reconstruído sempre que o runner muda em um deploy do Bencher Cloud.
Também pode ser definido com a variável de ambiente `BENCHER_UPDATE_CHANNEL`.
Conflita com `--no-auto-update`.

### `--max-download-size <MAX_DOWNLOAD_SIZE>`

O tamanho máximo de download em bytes para binários de auto-atualização.
Por padrão, `500` MiB é usado.
Conflita com `--no-auto-update`.

### `--max-output-size <MAX_OUTPUT_SIZE>`

O tamanho máximo em bytes para `stdout` e `stderr` coletados.
Por padrão, `25` MiB é usado.

### `--max-file-count <MAX_FILE_COUNT>`

O número máximo de arquivos de saída a decodificar.
Por padrão, `255` é usado.

### `--max-symlinks <MAX_SYMLINKS>`

O número máximo de symlinks a seguir durante a resolução de caminho,
correspondendo ao limite `MAXSYMLINKS` do kernel Linux.
Por padrão, `40` é usado.
Usado apenas no modo sem sandbox.
