## Pull Requests sur matériel dédié

GitHub Actions propose des runners auto-hébergés, mais ils vous obligent à utiliser
leur binaire bruyant [GitHub Actions Runner][github actions runner].
[Bencher Bare Metal][bare metal] exécute les benchmarks sur une flotte dédiée de matériel bare metal
à l'aide d'un runner de benchmark à faible bruit, conçu sur mesure.
De plus, Bencher Bare Metal prend en charge les PRs de forks,
alors que le GitHub Actions Runner ne le fait pas.

Une fois que vous êtes passé à Bencher Bare Metal,
vous ne voulez pas qu'un job GitHub Actions tourne pendant qu'il attend Bencher.
Pour résoudre ce problème, le workflow soumet le Job Bencher Bare Metal et se termine.
Lorsque le Job se termine, Bencher lui-même complète la vérification GitHub
et publie les résultats en tant que commentaire sur la Pull Request.

L'exemple suivant est destiné aux branches au sein du **même** dépôt.
Utilisez ce modèle conjointement avec
le workflow [Pull Requests depuis des Forks][pull requests from forks] ci-dessus
pour obtenir le benchmarking sur matériel dédié pour les PRs de forks.

Tout d'abord, liez le dépôt au Projet, une seule fois :

1. Dans la Console Bencher, ouvrez les `Settings` du Projet, puis `Connections`.
2. Sur la carte GitHub, cliquez sur `Link repository`.
   GitHub vous ramène à `Connections`, où la carte liste chaque dépôt sur lequel vous pouvez pousser.
3. Cliquez sur `Link` à côté du dépôt.
   S'il n'est pas listé, cliquez sur `Install on GitHub` et donnez à l'application l'accès à ce dépôt.
   S'il affiche `Approval required`, cliquez sur `Approve on GitHub`, approuvez les nouvelles permissions de l'application,
   puis rouvrez `Connections` et cliquez sur `Link repository`.

Lier un dépôt nécessite le rôle Maintainer sur le Projet, que détiennent les Leaders de l'Organisation et les administrateurs du serveur, et l'accès en push au dépôt.
L'application GitHub de Bencher a besoin d'un accès en lecture et en écriture aux checks et aux pull requests du dépôt,
et d'un accès en lecture à son contenu, elle ne peut donc pas pousser dans le dépôt.
Bencher crée un jeton pour le dépôt lié
et publie avec ce jeton la vérification GitHub et le commentaire sur la Pull Request.
Si la carte GitHub affiche `Disconnected`, cliquez sur `Install on GitHub` et redonnez à l'application l'accès au dépôt,
ou levez la suspension de son installation, et le lien se rétablit.
Pour Bencher Self-Hosted, le serveur a besoin de [sa propre application GitHub][github app] et de la version `v0.6.18` ou ultérieure.

> 🐰 Quiconque possède la clé d'API du Projet peut faire publier par Bencher une vérification GitHub ou un commentaire de Pull Request
> dans le dépôt lié, sur n'importe quel commit ou Pull Request de ce dépôt.
> Gardez le `BENCHER_API_KEY` secret comme tout autre secret.

1. Créez un fichier `workflow` GitHub Actions.
   (ex : `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Nommez ce workflow.
   (ex : `name: Bare Metal PR Benchmarks with Bencher`)
3. Exécutez sur des événements `pull_request`, comme dans [Pull Requests][pull requests] ci-dessus.
   (ex : `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. Créez un `job` GitHub Actions.
   (ex : `jobs: submit_pr_benchmarks`)
5. Exécutez sur des événements `pull_request` uniquement si la pull request vient du même dépôt.
   ⚠️ NE SUPPRIMEZ PAS CETTE LIGNE !
   Pour gérer les PRs de Forks, voir [Pull Requests depuis des Forks][pull requests from forks] ci-dessus.
   (ex : `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. Définissez [les permissions pour le `GITHUB_TOKEN`][github token permissions]
   sur `read` pour `contents`.
   Bencher publie la vérification GitHub et le commentaire, donc le workflow n'a besoin d'aucun accès en écriture.
   (ex : `permissions: contents: read`)
7. Définissez le type de machine sur laquelle le job s'exécutera.
   Il ne fait que soumettre le Job, donc une petite machine suffit.
   (ex : `runs-on: ubuntu-latest`)
8. Récupérez le code source de la branche PR.
   (ex : `uses: actions/checkout@v6`)
9. Installez le Bencher CLI en utilisant [l'Action GitHub][bencher cli github action].
   (ex : `uses: bencherdev/bencher@main`)
10. Utilisez la sous-commande CLI <code><a href="/fr/docs/explanation/bencher-run/">bencher run</a></code>
    pour soumettre vos benchmarks de branche de pull request.
    Voir [la sous-commande CLI `bencher run`][bencher run] pour un aperçu complet.
    (ex : `bencher run`)
11. Définissez l'option `--project` sur le slug du projet.
    Voir [la documentation `--project`][project option] pour plus de détails.
    (ex : `--project project-abc4567-wxyz123456789`)
12. Définissez l'option `--key` sur le secret du **dépôt** `BENCHER_API_KEY`.
    Voir [la documentation `--key`][key option] pour plus de détails.
    (ex : `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. Définissez l'option `--branch` sur le nom de la branche PR
    en utilisant [la variable d'environnement par défaut `GITHUB_HEAD_REF` de GitHub Actions][github default environment variables].
    Voir [la documentation `--branch`][branch option] pour un aperçu complet.
    (ex : `--branch "$GITHUB_HEAD_REF"`)
14. Définissez l'option `--hash` sur le hash `git` de la branche PR, comme dans [Pull Requests][pull requests] ci-dessus.
    Voir [la documentation `--hash`][hash option] pour un aperçu complet.
    (ex : `--hash '${{ github.event.pull_request.head.sha }}'`)
15. Définissez le point de départ de la branche PR, comme dans [Pull Requests][pull requests] ci-dessus.
    Voir [la documentation `--start-point`][start point] pour un aperçu complet.
    (ex : `--start-point "$GITHUB_BASE_REF"`)
16. Définissez l'option `--adapter` sur le [Format de Métrique Bencher JSON (`json`)][bmf] généré par <code><a href="/fr/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>.
    Voir [les adaptateurs de harnais de benchmark][adapter json] pour un aperçu complet.
    (ex : `--adapter json`)
17. Définissez l'option `--image` sur votre image pour matériel dédié.
    Voir [la documentation `--image`][image option] pour un aperçu complet.
    (ex : `--image project-abc4567-wxyz123456789:latest`)
18. Définissez le drapeau `--detach` pour vous terminer dès que le Job est soumis.
    Voir [la documentation `--detach`][detach option] pour plus de détails.
    (ex : `--detach`)
19. Définissez l'option `--github-actions` sur [la variable d'environnement `GITHUB_TOKEN` de GitHub Actions][github token].
    Avec `--detach`, `bencher run` envoie le dépôt, le commit de tête et le numéro de la Pull Request
    depuis l'événement GitHub Actions avec le Job, et ne fait aucune requête à GitHub avec le token.
    Voir [la documentation `--github-actions`][github actions option] pour plus de détails.
    (ex : `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. Spécifiez la commande de benchmark à exécuter dans l'image.
    La commande est transmise au point d'entrée de l'image, s'il y en a un (voir [l'option `--entrypoint`][entrypoint option]).
    Voir [la commande de benchmark][command argument] pour un aperçu complet.
    (ex : `bencher mock`)

Bencher refuse de soumettre le Job s'il ne peut pas publier les résultats :
le serveur n'a pas d'application GitHub, le Projet n'est pas réclamé,
ou le Projet n'a pas de dépôt lié et connecté pour le dépôt du workflow.
Après la soumission, Bencher démarre la vérification GitHub sur le commit de tête.
Lorsque le Job se termine, Bencher complète la vérification GitHub puis écrit le commentaire sur la Pull Request,
comme le décrit [l'option `--github-actions`][github actions option].
La vérification GitHub se conclut en échec si le Rapport a une Alerte ou si le Job échoue,
donc [le drapeau `--error-on-alert`][alert err] n'est pas nécessaire, et il est en conflit avec `--detach`.
Les options qui décident de la façon dont les résultats sont publiés, comme `--ci-only-on-alert` et `--ci-id`, vont dans la même commande,
et Bencher les conserve avec le Job.

La vérification GitHub appartient à l'application GitHub de Bencher, pas à GitHub Actions.
Si une règle de protection de branche ou un ensemble de règles [exige la vérification GitHub][github required status checks],
définissez l'application GitHub de Bencher comme sa source.
Sinon, GitHub attend une vérification GitHub de GitHub Actions qui ne vient jamais.

Si l'installation de l'application GitHub de Bencher n'a pas approuvé ses nouvelles permissions, Bencher ne peut pas publier les résultats.
Le Job enregistre l'échec avec un lien pour les approuver,
et `bencher run` affiche le lien s'il voit l'échec avant de se terminer.
Une fois les permissions approuvées, l'exécution suivante publie ses résultats.

Un Job sans Pull Request, par exemple issu d'un événement `push`, obtient une vérification GitHub et aucun commentaire.
Il en va de même pour un Job dont le commit n'est plus la tête de la Pull Request.
Si la Pull Request a aussi des exécutions du Projet sans `--detach`,
elle reçoit pour elles un second commentaire, du bot GitHub Actions.
