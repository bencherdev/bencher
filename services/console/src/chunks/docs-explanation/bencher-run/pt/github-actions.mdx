### `--github-actions <GITHUB_TOKEN>`

<br />

Opcional: Defina o token de autenticação da API do GitHub.
A maneira mais conveniente de fazer isso é usando a [variável de ambiente `GITHUB_TOKEN` do GitHub Actions][github token] (ou seja, `--github-actions ${{ secrets.GITHUB_TOKEN }}`).

Os resultados serão adicionados ao commit head como uma Verificação do GitHub chamada:

1. `Bencher Report (<ID>)` se [a opção `--ci-id`](#--ci-id-id) estiver definida
2. `Bencher Report (<NOME DO PROJETO>)` para Projetos existentes
3. `Bencher Report` para Projetos [`--ci-on-the-fly`](#--ci-on-the-fly) (enquanto estiver em andamento)

Isso requer que o token tenha [o escopo de `checks` com permissões de `write`][github token permissions].
Se a Verificação do GitHub não puder ser criada, o `bencher run` registrará um aviso e continuará.

Quando `bencher run` é usado como parte de um pull request,
os resultados também serão adicionados ao pull request como um comentário.
Todos os trabalhos de um Projeto no pull request compartilham este único comentário, com uma linha de Relatório para cada trabalho.
Isso requer que o token tenha [o escopo de `pull-requests` com permissões de `write`][github token permissions].
Os resultados também serão sempre adicionados ao resumo do trabalho.
Com [a flag `--detach`](/pt/docs/explanation/images/#--detach), a execução desanexada não publica nenhum comentário nem escreve o resumo do trabalho, e [a conexão com `--job`](/pt/docs/explanation/images/#--job-uuid) conclui a Verificação do GitHub que ela iniciou (veja [a opção `--ci-callback-token`](#--ci-callback-token-token)).

Com duas ou mais linhas, o comentário mostra uma tabela de resumo de cada Relatório com seu Ambiente de Teste, Adaptador e status (`Pending`, o número de Alertas, `No Alerts` ou `Failed`).
As linhas estão na ordem em que os Relatórios começaram, numeradas a partir de 1, como o Console lista os Relatórios de uma execução.
O rótulo de cada linha é o seu número, seguido do valor da [opção `--ci-id`](#--ci-id-id) entre parênteses, se ela estiver definida (ex: `2 (microbench)`).
O rótulo leva ao Relatório, o Ambiente de Teste à sua página no Console e o Adaptador à sua parte da [documentação de Adaptadores](/pt/docs/explanation/adapters/).
Quando os trabalhos usam mais de um Branch, a tabela de resumo ganha uma coluna para o Branch.
Em seguida, uma tabela reúne os Alertas de todos os Relatórios, com uma coluna para o Relatório.
Depois, os resultados de cada Relatório seguem em um bloco recolhível (ex: `Report 2 (microbench): 14 benchmarks, 2 alerts`),
que fica aberto quando o Relatório tem Alertas.
Cada trabalho mantém sua própria Verificação do GitHub e seu próprio resumo do trabalho,
então os nomes das Verificações do GitHub e as verificações de status obrigatórias não mudam.
Um trabalho cujo commit não é mais o commit head do pull request deixa o comentário como está.
Se o token não puder ler o pull request, então o trabalho registrará um aviso e escreverá o comentário sem verificar seu commit head.

Um comentário do GitHub tem um limite de tamanho, então o comentário usa a primeira destas formas que couber:

1. Todas as partes acima
2. Sem os blocos recolhíveis, com um aviso de que o comentário está truncado
3. Todas as linhas de resumo e o número total de Alertas, sem as linhas de Alertas
4. Como último recurso, as primeiras linhas de resumo, e depois `and N more reports` para o restante

Com uma única linha, o comentário é o mesmo de antes e, se for grande demais, leva ao Relatório completo.

Para encontrar os outros trabalhos, o `bencher run` lista as Verificações do GitHub do commit head,
o que o escopo de `checks` com permissões de `write` acima já permite.
Se um trabalho não conseguir criar ou concluir sua Verificação do GitHub, não conseguir identificar qual GitHub App é dona dela, ou não conseguir listar as Verificações do GitHub,
então ele publicará um comentário apenas com seus próprios resultados.
Os comentários do Projeto de uma versão anterior do `bencher run` são substituídos:
o primeiro trabalho a escrever o comentário compartilhado atualiza o mais antigo deles e exclui os demais.
Ao escrever o comentário compartilhado, um trabalho só atualiza ou exclui comentários publicados pela GitHub App dona da sua Verificação do GitHub,
o que com o `GITHUB_TOKEN` é o bot `github-actions`.

[github token]: https://docs.github.com/pt/actions/security-guides/automatic-token-authentication
[github token permissions]: https://docs.github.com/pt/actions/security-for-github-actions/security-guides/automatic-token-authentication#permissions-for-the-github_token

> 🐰 Se você estiver executando dentro de um contêiner Docker no GitHub Action, precisará passar as seguintes variáveis de ambiente e montar o caminho especificado por `GITHUB_EVENT_PATH`:
> - `GITHUB_ACTIONS`
> - `GITHUB_EVENT_NAME`
> - `GITHUB_EVENT_PATH`
> - `GITHUB_SHA`
> - `GITHUB_API_URL` (GitHub Enterprise Server apenas)
