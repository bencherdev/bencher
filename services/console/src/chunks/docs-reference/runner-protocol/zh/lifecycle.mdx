## Job 生命周期

每个 Job 在其各次执行被发送、运行和处理时，会经过一组固定的状态。
Job 从第一次执行起直到有结果为止都保持 `running`，在各次执行之间也是如此。

| 从        | 到          | 触发条件                                                               |
| --------- | ----------- | ---------------------------------------------------------------------- |
| pending   | claimed     | Runner 接收该 Job 的第一次执行                                    |
| pending   | canceled    | 用户取消该 Job                                                  |
| claimed   | running     | Runner 发送 `running`                                              |
| claimed   | failed      | Runner 发送 `failed`                                                     |
| claimed   | unknown     | 服务器与 Runner 失去联系                                                       |
| claimed   | canceled    | 用户取消该 Job                                                  |
| running   | completed   | 该 Job 的每次迭代都有了结果                                        |
| running   | failed      | 某次执行在没有 `allow_failure` 时失败，或 Job 的时间用完                 |
| running   | unknown     | 服务器与其唯一进行中执行的 Runner 失去联系                                     |
| running   | canceled    | 用户取消该 Job，或超过了硬性 Job 超时             |
| unknown   | running     | Runner 重新发送其结果，且 Job 还有剩余迭代                               |
| unknown   | completed   | Runner 重新发送其结果，且每次迭代都有了结果                              |
| unknown   | failed      | Runner 发送 `failed`                                                     |
| unknown   | canceled    | 用户取消该 Job，或超过了硬性 Job 超时                                                |
| completed | processed   | 服务器成功处理结果                          |
| completed | failed      | 服务器处理结果失败                                                              |
| completed | unknown     | 启动时，服务器发现已存储的结果丢失                                                      |

`processed`、`failed` 和 `canceled` 是终止状态：`failed` 或 `canceled` 的 Job 永远不会再改变状态。
`completed` 是准终止状态：
`completed` 在结果被解析后转换为 `processed`，在结果无法处理时转换为 `failed`，在服务器启动时发现结果丢失时转换为 `unknown`。
`unknown` 表示服务器已与 Runner 失去联系，尚不知道结果。
当 Runner 再次通信时，它会以 Runner 发送的结果解决；
当 Job 的截止时间过去时，它会以 `canceled` 解决。
每次转换在其数据库更新上都使用状态过滤器，
因此被并发修改的 Job 会被重新读取而不是被覆盖。
