## Pull Requests на выделенном оборудовании

У GitHub Actions есть Self-Hosted раннеры, но для них нужно использовать
их шумный бинарный файл [GitHub Actions Runner][github actions runner].
[Bencher Bare Metal][bare metal] запускает бенчмарки на выделенном парке оборудования bare metal
с помощью специально созданного малошумного раннера бенчмарков.
Кроме того, Bencher Bare Metal поддерживает PR из форков,
а GitHub Actions Runner нет.

После перехода на Bencher Bare Metal
вам не захочется, чтобы job GitHub Actions работал все время, пока он ждет Bencher.
Поэтому workflow отправляет Job в Bencher Bare Metal и завершается.
Когда Job завершается, Bencher сам завершает проверку GitHub
и публикует результаты как комментарий к Pull Request.

Следующий пример предназначен для веток в **том же** репозитории.
Используйте этот шаблон вместе с
workflow [Pull Requests из Fork][pull requests from forks] выше,
чтобы запускать бенчмарки на выделенном оборудовании для PR из форков.

Сначала один раз свяжите репозиторий с Проектом:

1. В Bencher Console откройте `Settings` Проекта, затем `Connections`.
2. На карточке GitHub нажмите `Link repository`.
   GitHub вернет вас в `Connections`, где карточка покажет каждый репозиторий, в который вы можете делать push.
3. Нажмите `Link` рядом с репозиторием.
   Если его нет в списке, нажмите `Install on GitHub` и дайте приложению доступ к нему.
   Если у него указано `Approval required`, нажмите `Approve on GitHub`, одобрите новые разрешения приложения,
   затем снова откройте `Connections` и нажмите `Link repository`.

Чтобы связать репозиторий, нужны роль Maintainer в Проекте, которая есть у Leader Организации и администраторов сервера, и доступ на push к репозиторию.
Приложению GitHub от Bencher нужен доступ на чтение и запись к checks и pull requests репозитория
и доступ на чтение к его содержимому, поэтому оно не может делать push в репозиторий.
Bencher создает токен для связанного репозитория
и публикует с ним проверку GitHub и комментарий к Pull Request.
Если на карточке GitHub указано `Disconnected`, нажмите `Install on GitHub` и снова дайте приложению доступ к репозиторию
или возобновите его приостановленную установку, и связь восстановится.
Для Bencher Self-Hosted серверу нужны [собственное приложение GitHub][github app] и версия `v0.6.18` или новее.
С лицензией Bencher Plus Enterprise сервер Bencher Self-Hosted может использовать [GitHub Enterprise Server][github enterprise server] вместо github.com.

> 🐰 Любой, у кого есть API-ключ Проекта, может заставить Bencher опубликовать проверку GitHub или комментарий к Pull Request
> в связанном репозитории, на любом коммите или Pull Request в нем.
> Храните `BENCHER_API_KEY` в секрете, как любой другой секрет.

1. Создайте файл `workflow` GitHub Actions.
   (пример: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Назовите этот workflow.
   (пример: `name: Bare Metal PR Benchmarks with Bencher`)
3. Запустите на событиях `pull_request`, как в разделе [Pull Requests][pull requests] выше.
   (пример: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. Создайте `job` GitHub Actions.
   (пример: `jobs: submit_pr_benchmarks`)
5. Запустите на событиях `pull_request` только в том случае, если pull request из того же репозитория.
   ⚠️ НЕ УДАЛЯЙТЕ ЭТУ СТРОКУ!
   Для обработки Fork PRs см. [Pull Requests из Fork][pull requests from forks] выше.
   (пример: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. Установите [разрешения для `GITHUB_TOKEN`][github token permissions]
   на `read` для `contents`.
   Bencher публикует проверку GitHub и комментарий, поэтому workflow не нужен доступ на запись.
   (пример: `permissions: contents: read`)
7. Установите тип машины, на которой будет выполняться job.
   Он только отправляет Job, поэтому достаточно небольшой машины.
   (пример: `runs-on: ubuntu-latest`)
8. Получите исходный код ветки PR.
   (пример: `uses: actions/checkout@v6`)
9. Установите Bencher CLI с использованием [GitHub Action][bencher cli github action].
   (пример: `uses: bencherdev/bencher@main`)
10. Используйте <code><a href="/ru/docs/explanation/bencher-run/">bencher run</a></code> CLI подкоманду
    для отправки бенчмарков ветки pull request.
    См. [подкоманду `bencher run` CLI][bencher run] для полного обзора.
    (пример: `bencher run`)
11. Установите опцию `--project` на идентификатор проекта.
    См. [документацию `--project`][project option] для подробностей.
    (пример: `--project project-abc4567-wxyz123456789`)
12. Установите опцию `--key` на **секрет** репозитория `BENCHER_API_KEY`.
    См. [документацию `--key`][key option] для подробностей.
    (пример: `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. Установите опцию `--branch` на имя ветки PR
    используя [переменную окружения `GITHUB_HEAD_REF` по умолчанию GitHub Actions][github default environment variables].
    См. [документацию `--branch`][branch option] для полного обзора.
    (пример: `--branch "$GITHUB_HEAD_REF"`)
14. Установите опцию `--hash` на `git` hash ветки PR, как в разделе [Pull Requests][pull requests] выше.
    См. [документацию `--hash`][hash option] для полного обзора.
    (пример: `--hash '${{ github.event.pull_request.head.sha }}'`)
15. Установите начальную точку для ветки PR, как в разделе [Pull Requests][pull requests] выше.
    См. [документацию `--start-point`][start point] для полного обзора.
    (пример: `--start-point "$GITHUB_BASE_REF"`)
16. Установите опцию `--adapter` на [Bencher Metric Format JSON (`json`)][bmf], который генерирует <code><a href="/ru/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>.
    См. [адаптеры тестовых харнесов][adapter json] для полного обзора.
    (пример: `--adapter json`)
17. Установите опцию `--image` на ваш образ для выделенного оборудования.
    См. [документацию `--image`][image option] для полного обзора.
    (пример: `--image project-abc4567-wxyz123456789:latest`)
18. Установите флаг `--detach`, чтобы завершиться сразу после отправки Job.
    См. [документацию `--detach`][detach option] для подробностей.
    (пример: `--detach`)
19. Установите опцию `--github-actions` на [переменную окружения `GITHUB_TOKEN` GitHub Actions][github token].
    С `--detach` команда `bencher run` отправляет вместе с Job репозиторий, head-коммит и номер Pull Request
    из события GitHub Actions и не делает запросов к GitHub с этим токеном.
    См. [документацию `--github-actions`][github actions option] для подробностей.
    (пример: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. Укажите команду бенчмарка, которая выполняется в образе.
    Команда передается точке входа образа, если она есть (см. [опцию `--entrypoint`][entrypoint option]).
    См. [команду бенчмарка][command argument] для полного обзора.
    (пример: `bencher mock`)

Bencher отказывается принять Job, если не может опубликовать результаты:
у сервера нет приложения GitHub, Проект невостребован,
или у Проекта нет подключенного связанного репозитория для репозитория workflow.
После отправки Bencher запускает проверку GitHub на head-коммите.
Когда Job завершается, Bencher завершает проверку GitHub, а затем пишет комментарий к Pull Request,
как описывает [опция `--github-actions`][github actions option].
Проверка GitHub завершается неудачей, если в Отчете есть предупреждение или Job завершился с ошибкой,
поэтому [флаг `--error-on-alert`][alert err] не нужен, и он конфликтует с `--detach`.
Опции, которые определяют, как публикуются результаты, например `--ci-only-on-alert` и `--ci-id`, указываются в той же команде,
и Bencher хранит их вместе с Job.

Проверка GitHub принадлежит приложению GitHub от Bencher, а не GitHub Actions.
Если правило защиты ветки или набор правил [требует эту проверку GitHub][github required status checks],
укажите приложение GitHub от Bencher как ее источник.
Иначе GitHub будет ждать проверку GitHub от GitHub Actions, которая никогда не придет.

Если установка приложения GitHub от Bencher не одобрила его новые разрешения, Bencher не может опубликовать результаты.
Job сохраняет ошибку со ссылкой для их одобрения,
а `bencher run` выводит эту ссылку, если видит ошибку до своего завершения.
После одобрения разрешений следующий запуск публикует свои результаты.

Job без Pull Request, например от события `push`, получает проверку GitHub и не получает комментарий.
То же относится к Job, чей коммит больше не является head-коммитом Pull Request.
Если у Pull Request есть и запуски Проекта без `--detach`,
он получает для них второй комментарий, от бота GitHub Actions.
