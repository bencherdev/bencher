## Job Lifecycle

Each Job moves through a fixed set of states as it is claimed, executed, and processed.

| From      | To          | Trigger                                                                |
| --------- | ----------- | ---------------------------------------------------------------------- |
| pending   | claimed     | A Runner claims the Job                                                 |
| pending   | canceled    | A user cancels the Job                                                  |
| claimed   | running     | The Runner sends `running`                                              |
| claimed   | failed      | The Runner sends `failed`                                              |
| claimed   | unknown     | The server loses contact with the Runner                               |
| claimed   | canceled    | A user cancels the Job                                                  |
| running   | completed   | The Runner sends `completed`                                            |
| running   | failed      | The Runner sends `failed`                                              |
| running   | unknown     | The server loses contact with the Runner                               |
| running   | canceled    | A user cancels the Job, or the hard Job timeout is exceeded             |
| unknown   | completed   | The Runner sends `completed`                                           |
| unknown   | failed      | The Runner sends `failed`                                              |
| unknown   | canceled    | A user cancels the Job, or the hard Job timeout is exceeded            |
| completed | processed   | The server successfully processes the results                          |
| completed | failed      | The server fails to process the results                                |
| completed | unknown     | At startup, the server finds the stored results were lost              |

`processed`, `failed`, and `canceled` are terminal: a `failed` or `canceled` Job never changes state again.
`completed` is quasi-terminal:
`completed` transitions to `processed` once the results are parsed, to `failed` if they cannot be processed, or to `unknown` if the server finds at startup that they were lost.
`unknown` means the server has lost contact with the Runner and does not yet know the outcome.
It is resolved when the Runner speaks again, with the result it sends,
or as `canceled` when the Job's deadline passes.
Every transition uses a status filter on its database update,
so a Job that was concurrently modified is re-read rather than overwritten.
