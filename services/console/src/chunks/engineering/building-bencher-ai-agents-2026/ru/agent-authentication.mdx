## Аутентификация агентов

До появления Bencher Bare Metal вся аутентификация строилась на JWT. Большие, красивые, непостижимые JWT. Аутентификация для раннеров Bare Metal использовала API-ключ с префиксом в имени, например `bencher_runner_abc123...`.

На стороне клиента я хотел дать агентам что-то для работы, помимо собственного JWT API-токена пользователя. Золотой серединой, которую я нашёл, стала наконец-то реализованная давно запрошенная функция: аутентификация с областью действия на уровне проекта. Claude помог мне создать безопасные API-ключи с префиксом и областью действия на уровне проекта. Права этих API-ключей ограничены тем, что выполняет [команда CLI `bencher run`][bencher run]: чтение в рамках проекта и неразрушающая запись. Благодаря этому такие API-ключи также естественно подходят для использования в CI-процессах непрерывного бенчмаркинга.

Позже, когда я добавил [Bencher MCP][bencher mcp], эти API-ключи с областью действия на уровне проекта стали использоваться для аутентификации и там. Стандарт MCP называет OAuth 2.1, однако он [всё ещё в статусе черновика][ietf oauth 2.1], поэтому я пока не хотел его реализовывать. Честно говоря, я довольно скептически отношусь к MCP. Я по-прежнему считаю, что хороший CLI + [навыки][bencher skills] представляют собой более эффективный и переносимый способ открыть сервис агенту. Однако самая большая проблема CLI в том, что у них нет стандартного механизма аутентификации. Так что, хотя OAuth 2.1 всё ещё черновик, по крайней мере в MCP это закрыто. А хорошая история с аутентификацией _действительно_ важна для enterprise.
