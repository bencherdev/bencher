### `--github-actions <GITHUB_TOKEN>`

<br />

Opcional: Establezca el token de autenticación de la API de GitHub.
La forma más conveniente de hacer esto es la [variable de entorno `GITHUB_TOKEN` de GitHub Actions][github token] (es decir, `--github-actions ${{ secrets.GITHUB_TOKEN }}`).

Los resultados se agregarán como una Verificación de GitHub al commit de encabezado, con el nombre:

1. `Bencher Report (<ID>)` si [la opción `--ci-id`](#--ci-id-id) está configurada
2. `Bencher Report (<NOMBRE DEL PROYECTO>)` para Proyectos existentes
3. `Bencher Report` para Proyectos [`--ci-on-the-fly`](#--ci-on-the-fly) (mientras está en curso)

Esto requiere que el token tenga [el alcance `checks` con permisos de `write`][github token permissions].
Si no se puede crear la Verificación de GitHub, entonces `bencher run` registrará una advertencia y continuará.

Cuando `bencher run` se utiliza como parte de una solicitud de extracción,
los resultados también se agregarán a la solicitud de extracción como un comentario.
Todos los trabajos de un Proyecto en la solicitud de extracción comparten este único comentario, con una sección para cada trabajo.
Esto requiere que el token tenga [el alcance `pull-requests` con permisos de `write`][github token permissions].
Los resultados siempre se agregarán también al resumen del trabajo.
Con [la bandera `--detach`](/es/docs/explanation/images/#--detach), la ejecución desacoplada no publica ningún comentario ni escribe el resumen del trabajo, y [la conexión con `--job`](/es/docs/explanation/images/#--job-uuid) completa la Verificación de GitHub que inició (consulte [la opción `--ci-callback-token`](#--ci-callback-token-token)).

La sección de cada trabajo se nombra según [la opción `--ci-id`](#--ci-id-id) si está configurada,
y de lo contrario según la Rama, el Banco de pruebas y el Adaptador del trabajo.
Con dos o más secciones, el comentario muestra una fila de resumen para cada sección con su estado (`Pending`, el número de Alertas, `No Alerts` o `Failed`),
una tabla con todas las Alertas
y los resultados de cada sección en un bloque desplegable que está abierto cuando la sección tiene Alertas.
Cada trabajo conserva su propia Verificación de GitHub y su propio resumen del trabajo,
por lo que los nombres de las Verificaciones de GitHub y las verificaciones de estado requeridas no cambian.
Un trabajo cuyo commit ya no es el commit de encabezado de la solicitud de extracción deja el comentario tal como está.
Si el token no puede leer la solicitud de extracción, entonces el trabajo registrará una advertencia y escribirá el comentario sin comprobar su commit de encabezado.

Para encontrar las demás secciones, `bencher run` lista las Verificaciones de GitHub del commit de encabezado,
lo cual ya permite el alcance `checks` con permisos de `write` mencionado arriba.
Si un trabajo no puede crear o completar su Verificación de GitHub, no puede determinar qué GitHub App es su propietaria, o no puede listar las Verificaciones de GitHub,
entonces publicará un comentario solo con sus propios resultados.
Los comentarios del Proyecto de una versión anterior de `bencher run` se reemplazan:
el primer trabajo que escribe el comentario compartido actualiza el más antiguo de ellos y elimina el resto.
Al escribir el comentario compartido, un trabajo solo actualiza o elimina los comentarios publicados por la GitHub App propietaria de su Verificación de GitHub,
que con el `GITHUB_TOKEN` es el bot `github-actions`.

[github token]: https://docs.github.com/es/actions/security-guides/automatic-token-authentication
[github token permissions]: https://docs.github.com/es/actions/security-for-github-actions/security-guides/automatic-token-authentication#permissions-for-the-github_token

> 🐰 Si está ejecutando dentro de un contenedor Docker dentro de una GitHub Action, necesitará pasar las siguientes variables de entorno y montar la ruta especificada por `GITHUB_EVENT_PATH`:
> - `GITHUB_ACTIONS`
> - `GITHUB_EVENT_NAME`
> - `GITHUB_EVENT_PATH`
> - `GITHUB_SHA`
> - `GITHUB_API_URL` (GitHub Enterprise Server solamente)
