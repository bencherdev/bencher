## ベアメタル上のプルリクエスト

GitHub Actionsにはセルフホストランナーがありますが、
GitHubのノイズの多い[GitHub Actions Runner][github actions runner]バイナリを使用する必要があります。
[Bencher Bare Metal][bare metal]は、専用のベアメタルハードウェアのフリート上で、
目的に特化した低ノイズのベンチマークランナーを使用してベンチマークを実行します。
さらに、Bencher Bare MetalはフォークからのPRをサポートしていますが、
GitHub Actions Runnerはサポートしていません。

Bencher Bare Metalに切り替えたら、
Bencherを待っている間ずっとGitHub Actionsのジョブを実行させておきたくはないはずです。
これを解決するために、ワークフローはBencher Bare MetalのJobを送信して終了します。
Jobが終了すると、Bencher自身がGitHubチェックを完了し、
結果をプルリクエストのコメントとして投稿します。

次の例は、**同じ**リポジトリ内のブランチで使用するためのものです。
フォークからのPRでベアメタルのベンチマークを行うには、
このパターンを上記の[フォークからのプルリクエスト][pull requests from forks]のワークフローと組み合わせて使用してください。

まず、リポジトリをプロジェクトに一度だけリンクします。

1. Bencher Consoleで、プロジェクトの`Settings`を開き、次に`Connections`を開きます。
2. GitHubカードで`Link repository`をクリックします。
   GitHubから`Connections`に戻ると、カードにはプッシュできる各リポジトリが一覧表示されます。
3. リポジトリの横にある`Link`をクリックします。
   一覧にない場合は、`Install on GitHub`をクリックし、そのリポジトリへのアクセスをアプリに許可します。
   `Approval required`と表示されている場合は、`Approve on GitHub`をクリックしてアプリの新しい権限を承認し、`Connections`を開き直して`Link repository`をクリックします。

リンクするには、プロジェクトのMaintainerロール（組織のLeaderとサーバー管理者が持つロール）と、リポジトリへのプッシュアクセスが必要です。
BencherのGitHub Appには、リポジトリのチェックとプルリクエストへの読み取りと書き込みのアクセスと、コンテンツへの読み取りアクセスが必要です。そのため、アプリはリポジトリにプッシュできません。
Bencherはリンクされたリポジトリ用のトークンを作成し、そのトークンでGitHubチェックとプルリクエストのコメントを投稿します。
GitHubカードに`Disconnected`と表示されている場合は、`Install on GitHub`をクリックしてリポジトリへのアクセスをアプリに再び許可するか、アプリのインストールの一時停止を解除すると、リンクが再接続されます。
Bencher Self-Hostedの場合、サーバーには[独自のGitHub App][github app]と`v0.6.18`以降のバージョンが必要です。
Bencher Plus Enterprise ライセンスがあれば、Bencher Self-Hosted サーバーは github.com の代わりに [GitHub Enterprise Server][github enterprise server] を使えます。

> 🐰 プロジェクトのAPIキーを持つ人は誰でも、リンクされたリポジトリのどのコミットやプルリクエストにも、
> BencherにGitHubチェックやプルリクエストのコメントを投稿させることができます。
> `BENCHER_API_KEY`は他のシークレットと同じように秘密にしてください。

1. GitHub Actionsの`workflow`ファイルを作成します。
   (例: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. このワークフローに名前を付けます。
   (例: `name: Bare Metal PR Benchmarks with Bencher`)
3. 上記の[プルリクエスト][pull requests]と同じように、`pull_request`イベントに応じて実行します。
   (例: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. GitHub Actionsの`job`を作成します。
   (例: `jobs: submit_pr_benchmarks`)
5. プルリクエストが同じリポジトリからの場合にのみ`pull_request`イベントを実行します。
   ⚠️この行を削除しないでください！
   フォークからのPRの処理については、上記の[フォークからのプルリクエスト][pull requests from forks]を参照してください。
   (例: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. [`GITHUB_TOKEN`の権限][github token permissions]を`contents`に対して`read`に設定します。
   BencherがGitHubチェックとコメントを投稿するため、ワークフローに書き込みアクセスは不要です。
   (例: `permissions: contents: read`)
7. ジョブが実行されるマシンタイプを設定します。
   Jobを送信するだけなので、小さなマシンで十分です。
   (例: `runs-on: ubuntu-latest`)
8. PRブランチのソースコードをチェックアウトします。
   (例: `uses: actions/checkout@v6`)
9. [GitHub Actionから][bencher cli github action]Bencher CLIをインストールします。
   (例: `uses: bencherdev/bencher@main`)
10. プルリクエストブランチのベンチマークを送信するために、<code><a href="/ja/docs/explanation/bencher-run/">bencher run</a></code> CLIサブコマンドを使用します。
    [`bencher run` CLIサブコマンド][bencher run]を参照し、全体を把握してください。
    (例: `bencher run`)
11. `--project`オプションをプロジェクトのスラッグに設定します。
    詳細は[`--project`ドキュメント][project option]を参照してください。
    (例: `--project project-abc4567-wxyz123456789`)
12. `--key`オプションを`BENCHER_API_KEY` **リポジトリ**シークレットに設定します。
    詳細は[`--key`ドキュメント][key option]を参照してください。
    (例: `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. [`GITHUB_HEAD_REF`のGitHub Actionsデフォルト環境変数][github default environment variables]を使用して、`--branch`オプションをPRブランチ名に設定します。
    全体を把握するために[`--branch`ドキュメント][branch option]を参照してください。
    (例: `--branch "$GITHUB_HEAD_REF"`)
14. 上記の[プルリクエスト][pull requests]と同じように、`--hash`オプションをPRブランチの`git`ハッシュに設定します。
    全体を把握するために[`--hash`ドキュメント][hash option]を参照してください。
    (例: `--hash '${{ github.event.pull_request.head.sha }}'`)
15. 上記の[プルリクエスト][pull requests]と同じように、PRブランチの開始ポイントを設定します。
    全体を把握するために[`--start-point`ドキュメント][start point]を参照してください。
    (例: `--start-point "$GITHUB_BASE_REF"`)
16. `--adapter`オプションを、<code><a href="/ja/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>が生成する[Bencher Metric Format JSON (`json`)][bmf]に設定します。
    全体を把握するために[ベンチマークハーネスアダプター][adapter json]を参照してください。
    (例: `--adapter json`)
17. `--image`オプションをベアメタル用のイメージに設定します。
    全体を把握するために[`--image`ドキュメント][image option]を参照してください。
    (例: `--image project-abc4567-wxyz123456789:latest`)
18. Jobを送信したらすぐに終了するように`--detach`フラグを設定します。
    詳細は[`--detach`ドキュメント][detach option]を参照してください。
    (例: `--detach`)
19. `--github-actions`オプションに[GitHub Actionsの`GITHUB_TOKEN`環境変数][github token]を設定します。
    `--detach`を指定すると、`bencher run`はGitHub Actionsのイベントからリポジトリ、ヘッドコミット、プルリクエスト番号をJobと一緒に送信し、トークンを使ったGitHubへのリクエストは行いません。
    詳細は[`--github-actions`ドキュメント][github actions option]を参照してください。
    (例: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. イメージ内で実行するベンチマークコマンドを指定します。
    コマンドは、イメージにエントリポイントがある場合はそのエントリポイントに渡されます（[`--entrypoint`オプション][entrypoint option]を参照）。
    全体を把握するために[ベンチマークコマンド][command argument]を参照してください。
    (例: `bencher mock`)

Bencherが結果を投稿できない場合、BencherはJobの送信を拒否します。
つまり、サーバーにGitHub Appがない場合、プロジェクトが未請求の場合、またはワークフローのリポジトリに対して接続済みのリンクされたリポジトリがプロジェクトにない場合です。
送信の後、Bencherはヘッドコミットに対してGitHubチェックを開始します。
Jobが終了すると、Bencherは[`--github-actions`オプション][github actions option]の説明どおりに、GitHubチェックを完了してからプルリクエストのコメントを書き込みます。
レポートにアラートがある場合、またはJobが失敗した場合、GitHubチェックは失敗として完了します。
そのため[`--error-on-alert`フラグ][alert err]は不要で、`--detach`とは競合します。
`--ci-only-on-alert`や`--ci-id`など、結果の投稿方法を決めるオプションは同じコマンドに指定し、BencherはそれらをJobと一緒に保存します。

GitHubチェックはGitHub ActionsではなくBencherのGitHub Appに属します。
ブランチ保護ルールまたはルールセットが[GitHubチェックを必須にしている][github required status checks]場合は、そのソースとしてBencherのGitHub Appを設定してください。
そうしないと、GitHubは決して来ないGitHub ActionsからのGitHubチェックを待ち続けます。

BencherのGitHub Appのインストールが新しい権限を承認していない場合、Bencherは結果を投稿できません。
Jobは承認用のリンクとともに失敗を記録し、`bencher run`は終了前にその失敗を確認できればリンクを表示します。
権限が承認されると、次の実行から結果が投稿されます。

`push`イベントからのJobなど、プルリクエストのないJobには、GitHubチェックが作成され、コメントは投稿されません。
コミットがもはやプルリクエストのヘッドではないJobも同様です。
プルリクエストに`--detach`なしのプロジェクトの実行もある場合、それらの実行にはGitHub Actionsのボットから2つ目のコメントが投稿されます。
