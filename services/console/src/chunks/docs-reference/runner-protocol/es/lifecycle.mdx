## Ciclo de Vida del Job

Cada Job recorre un conjunto fijo de estados a medida que sus ejecuciones se envían, se ejecutan y se procesan.
Un Job permanece `running` desde su primera ejecución hasta su resultado, también entre sus ejecuciones.

| Desde     | Hacia       | Disparador                                                             |
| --------- | ----------- | ---------------------------------------------------------------------- |
| pending   | claimed     | Un Runner toma la primera ejecución del Job                             |
| pending   | canceled    | Un usuario cancela el Job                                               |
| claimed   | running     | El Runner envía `running`                                               |
| claimed   | failed      | El Runner envía `failed`                                               |
| claimed   | unknown     | El servidor pierde el contacto con el Runner                           |
| claimed   | canceled    | Un usuario cancela el Job                                               |
| running   | completed   | Cada iteración del Job tiene su resultado                               |
| running   | failed      | Una ejecución falla sin `allow_failure`, o se agota el tiempo del Job  |
| running   | unknown     | El servidor pierde el contacto con el Runner de su única ejecución en curso |
| running   | canceled    | Un usuario cancela el Job, o se excede el tiempo de espera duro del Job |
| unknown   | running     | El Runner reenvía su resultado, y al Job le quedan iteraciones         |
| unknown   | completed   | El Runner reenvía su resultado, y cada iteración tiene su resultado    |
| unknown   | failed      | El Runner envía `failed`                                               |
| unknown   | canceled    | Un usuario cancela el Job, o se excede el tiempo de espera duro del Job |
| completed | processed   | El servidor procesa correctamente los resultados                       |
| completed | failed      | El servidor no logra procesar los resultados                           |
| completed | unknown     | Al arrancar, el servidor descubre que los resultados almacenados se perdieron |

`processed`, `failed` y `canceled` son terminales: un Job `failed` o `canceled` nunca vuelve a cambiar de estado.
`completed` es cuasi-terminal:
`completed` pasa a `processed` una vez que se analizan los resultados, a `failed` si no se pueden procesar, o a `unknown` si al arrancar el servidor descubre que se perdieron.
`unknown` significa que el servidor perdió el contacto con el Runner y aún no conoce el resultado.
Se resuelve cuando el Runner vuelve a comunicarse, con el resultado que envía,
o como `canceled` cuando vence el plazo del Job.
Cada transición usa un filtro de estado en su actualización de base de datos,
de modo que un Job que fue modificado de forma concurrente se vuelve a leer en lugar de sobrescribirse.
