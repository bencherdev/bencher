## Pull Requests em hardware dedicado

O GitHub Actions tem runners auto-hospedados, mas eles exigem que você use
o binário ruidoso [GitHub Actions Runner][github actions runner] deles.
O [Bencher Bare Metal][bare metal] executa benchmarks em uma frota dedicada de hardware bare metal
usando um runner de benchmark de baixo ruído, construído sob medida.
Além disso, o Bencher Bare Metal suporta PRs de forks,
enquanto o GitHub Actions Runner não.

Depois de migrar para o Bencher Bare Metal,
você não vai querer um job do GitHub Actions em execução enquanto ele aguarda o Bencher.
Para resolver isso, o Bencher usa um workflow dividido para que o GitHub Actions
possa aguardar os Jobs do Bencher Bare Metal de forma assíncrona.

O exemplo a seguir é para branches dentro do **mesmo** repositório.
Use este padrão em conjunto com
o workflow de [Pull Requests de Forks][pull requests from forks] acima
para obter benchmarks em hardware dedicado para PRs de forks.

Primeiro, vincule o repositório ao Projeto, uma única vez:

1. No Bencher Console, abra os `Settings` do Projeto e depois `Connections`.
2. No cartão do GitHub, clique em `Link repository`.
   O GitHub traz você de volta a `Connections`, onde o cartão lista cada repositório para o qual você pode fazer push.
3. Clique em `Link` ao lado do repositório.
   Se ele não estiver listado, clique em `Install on GitHub` e dê ao aplicativo acesso a ele.
   Se ele mostrar `Approval required`, clique em `Approve on GitHub`, aprove as novas permissões do aplicativo
   e depois abra `Connections` novamente e clique em `Link repository`.

Vincular exige a função Maintainer no Projeto, que os Leaders da Organização e os administradores do servidor têm, e acesso de push ao repositório.
O aplicativo GitHub do Bencher precisa de acesso de leitura e escrita ao conteúdo do repositório,
porque o `repository_dispatch` não aceita nada menos.
Quando um Job termina, o Bencher cria um token para o repositório vinculado
e envia o evento `repository_dispatch` com ele.
Se o cartão do GitHub mostrar `Disconnected`, clique em `Install on GitHub` e dê ao aplicativo acesso ao repositório novamente,
ou reative a instalação suspensa, e o vínculo se restabelece.
Para o Bencher Self-Hosted, o servidor precisa de [seu próprio aplicativo GitHub][github app] e da versão `v0.6.16` ou posterior.

<PullRequestsOnBareMetalSubmitCode />

1. Crie um primeiro arquivo `workflow` do GitHub Actions.
   (ex: `.github/workflows/pr_bare_metal_benchmarks.yml`)
2. Nomeie esse workflow.
   (ex: `name: Bare Metal PR Benchmarks with Bencher`)
3. Execute em eventos de `pull_request`, como em [Pull Requests][pull requests] acima.
   (ex: `on: pull_request: types: [opened, reopened, edited, synchronize]`)
4. Crie um `job` no GitHub Actions.
   (ex: `jobs: submit_pr_benchmarks`)
5. Execute em eventos de `pull_request` se, e somente se o pull request for do mesmo repositório.
   ⚠️ NÃO REMOVA ESTA LINHA!
   Para lidar com PRs de Forks veja [Pull Requests de Forks][pull requests from forks] acima.
   (ex: `if: github.event_name == 'pull_request' && github.event.pull_request.head.repo.full_name == github.repository`)
6. Defina [as permissões para o `GITHUB_TOKEN`][github token permissions]
   como `write` para `checks`.
   O primeiro workflow inicia a Verificação do GitHub e não publica nenhum comentário.
   (ex: `permissions: checks: write`)
7. Defina o tipo de máquina em que o job será executado.
   Ele apenas envia o Job, então uma máquina pequena é suficiente.
   (ex: `runs-on: ubuntu-latest`)
8. Faça o checkout do código fonte da branch do PR.
   (ex: `uses: actions/checkout@v6`)
9. Instale o Bencher CLI usando [a GitHub Action][bencher cli github action].
   (ex: `uses: bencherdev/bencher@main`)
10. Use o subcomando CLI <code><a href="/pt/docs/explanation/bencher-run/">bencher run</a></code>
    para enviar seus benchmarks da branch do pull request.
    Veja [o subcomando CLI `bencher run`][bencher run] para uma visão geral completa.
    (ex: `bencher run`)
11. Defina a opção `--project` para o slug do Projeto.
    Veja [a documentação `--project`][project option] para mais detalhes.
    (ex: `--project project-abc4567-wxyz123456789`)
12. Defina a opção `--key` para o segredo **Repositório** `BENCHER_API_KEY`.
    Veja [a documentação `--key`][key option] para mais detalhes.
    (ex: `--key '${{ secrets.BENCHER_API_KEY }}'`)
13. Defina a opção `--branch` para o nome da branch do PR
    usando [a variável de ambiente padrão `GITHUB_HEAD_REF` do GitHub Actions][github default environment variables].
    Veja [a documentação `--branch`][branch option] para uma visão geral completa.
    (ex: `--branch "$GITHUB_HEAD_REF"`)
14. Defina a opção `--hash` para o hash `git` da branch do PR, como em [Pull Requests][pull requests] acima.
    Veja [a documentação `--hash`][hash option] para uma visão geral completa.
    (ex: `--hash '${{ github.event.pull_request.head.sha }}'`)
15. Defina o Ponto de Início para a Branch do PR, como em [Pull Requests][pull requests] acima.
    Veja [a documentação `--start-point`][start point] para uma visão geral completa.
    (ex: `--start-point "$GITHUB_BASE_REF"`)
16. Defina a opção `--adapter` para o [Bencher Metric Format JSON (`json`)][bmf] gerado pelo <code><a href="/pt/docs/reference/bencher-metric-format/#bencher-mock">bencher mock</a></code>.
    Veja [adaptadores de harness de benchmark][adapter json] para uma visão geral completa.
    (ex: `--adapter json`)
17. Defina a opção `--image` para a sua imagem para hardware dedicado.
    Veja [a documentação `--image`][image option] para uma visão geral completa.
    (ex: `--image project-abc4567-wxyz123456789:latest`)
18. Defina a flag `--detach` para terminar assim que o Job for enviado.
    Veja [a documentação `--detach`][detach option] para mais detalhes.
    (ex: `--detach`)
19. Defina a opção `--github-actions` para o token de autenticação da API do GitHub para iniciar a Verificação do GitHub usando
    [a variável de ambiente `GITHUB_TOKEN` do GitHub Actions][github token].
    Veja [a documentação `--github-actions`][github actions option] para mais detalhes.
    (ex: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
20. Especifique o comando de benchmark a ser executado na imagem.
    O comando é passado ao entrypoint da imagem, se ela tiver um (veja [a opção `--entrypoint`][entrypoint option]).
    Veja [comando de benchmark][command argument] para uma visão geral completa.
    (ex: `bencher mock`)

No GitHub Enterprise Server, ou para manter seu próprio token, defina a opção `--ci-callback-token`
para um [token de acesso pessoal de granularidade fina][github fine-grained token]
com acesso de leitura e escrita ao conteúdo do repositório, armazenado como o segredo **Repositório** `BENCHER_CALLBACK_TOKEN`.
O Bencher envia o evento `repository_dispatch` com esse token, quer o Projeto tenha um repositório vinculado ou não.
Veja [a documentação `--ci-callback-token`][ci callback token option] para mais detalhes.
(ex: `--ci-callback-token '${{ secrets.BENCHER_CALLBACK_TOKEN }}'`)

<PullRequestsOnBareMetalAttachCode />

1. Crie um segundo arquivo `workflow` do GitHub Actions na sua branch padrão.
   O GitHub só executa um workflow de `repository_dispatch` a partir da branch padrão,
   então, até que este arquivo esteja lá, a Verificação do GitHub que o primeiro workflow inicia permanece em andamento.
   (ex: `.github/workflows/pr_bare_metal_benchmarks_attach.yml`)
2. Nomeie esse workflow.
   (ex: `name: Attach Bare Metal PR Benchmarks with Bencher`)
3. Execute em eventos de `repository_dispatch` do tipo `bencher_run`.
   Veja a [documentação `on` do GitHub Actions][github actions on]
   e a [documentação `repository_dispatch` do GitHub Actions][github repository_dispatch] para uma visão geral completa.
   (ex: `on: repository_dispatch: types: [bencher_run]`)
4. Crie um `job` no GitHub Actions.
   (ex: `jobs: attach_pr_benchmarks`)
5. Defina [as permissões para o `GITHUB_TOKEN`][github token permissions]
   como `write` para `checks` e `pull-requests`.
   (ex: `permissions: checks: write pull-requests: write`)
6. Defina o tipo de máquina em que o job será executado.
   O Job já terminou, então este job apenas publica os resultados.
   (ex: `runs-on: ubuntu-latest`)
7. Instale o Bencher CLI usando [a GitHub Action][bencher cli github action].
   Nenhum checkout é necessário.
   (ex: `uses: bencherdev/bencher@main`)
8. Passe o UUID do Job do evento por meio de [uma variável de ambiente intermediária][github intermediate environment variable],
   nunca diretamente em `run:`, como orienta o guia do GitHub sobre injeção de scripts.
   (ex: `env: JOB_UUID: ${{ github.event.client_payload.bencher.job }}`)
9. Use o subcomando CLI <code><a href="/pt/docs/explanation/bencher-run/">bencher run</a></code>
   para se conectar ao Job.
   Veja [o subcomando CLI `bencher run`][bencher run] para uma visão geral completa.
   (ex: `bencher run`)
10. Defina a opção `--project` para o slug do Projeto.
    Se o repositório tiver mais de um Projeto, passe `github.event.client_payload.bencher.project` por uma variável de ambiente da mesma forma
    e coloque-a entre aspas (ex: `--project "$PROJECT_SLUG"`).
    Veja [a documentação `--project`][project option] para mais detalhes.
    (ex: `--project project-abc4567-wxyz123456789`)
11. Defina a opção `--key` para o segredo **Repositório** `BENCHER_API_KEY`.
    Veja [a documentação `--key`][key option] para mais detalhes.
    (ex: `--key '${{ secrets.BENCHER_API_KEY }}'`)
12. Defina a opção `--job` para o UUID do Job entre aspas.
    Veja [a documentação `--job`][job option] para uma visão geral completa.
    (ex: `--job "$JOB_UUID"`)
13. Defina a flag `--error-on-alert` para falhar o comando se um Alerta for gerado.
    O evento carrega apenas dados, então as opções que decidem como os resultados são publicados, como `--ci-only-on-alert` e `--ci-public-links`, também ficam aqui, no segundo workflow.
    Veja [a documentação `--error-on-alert`][alert err] para uma visão geral completa.
    (ex: `--error-on-alert`)
14. Defina a opção `--github-actions` para o token de autenticação da API do GitHub para publicar os resultados como uma Verificação do GitHub e um comentário no Pull Request usando
    [a variável de ambiente `GITHUB_TOKEN` do GitHub Actions][github token].
    Um `--ci-number` ou `--ci-id` explícito aqui tem prioridade sobre o evento.
    Veja [a documentação `--github-actions`][github actions option] para mais detalhes.
    (ex: `--github-actions '${{ secrets.GITHUB_TOKEN }}'`)
