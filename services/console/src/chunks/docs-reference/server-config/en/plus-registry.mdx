### `plus.registry`

This section specifies the container registry storage configuration.
Bencher can function as an OCI-compliant container/artifact registry.

If this section is not configured, Bencher will use local filesystem storage
in a `registry` directory sibling to the database file.
This is suitable for development and single-instance deployments.

For production deployments with multiple instances or for durability,
configure S3-compatible storage.

There are two storage `scheme`s:
- `file`: Store registry artifacts on the local filesystem (default)
    - `path`: (Optional) Directory for registry data. Defaults to a `registry` directory sibling to the database file.
- `s3`: Store registry artifacts in any S3 compatible blob storage
    - `bucket`: Bucket name
    - `path`: (Optional) Key prefix in bucket. Leading, trailing, and repeated slashes are dropped, so `registry`, `registry/`, and `/registry` all store under `registry`.
    - `endpoint`: (AWS: Optional | Non-AWS: Required) Storage endpoint
    - `region`: (Optional) Bucket region. Required for AWS. Defaults to `auto`, which S3 compatible stores expect.
    - `access_key_id`: S3 access key
    - `secret_access_key`: S3 secret access key
    - `chunk_size`: (Optional) Minimum chunk size in bytes for buffering upload data before storing. Defaults to 5 MB.
      HTTP request bodies arrive as small network frames (typically 8 to 64 KB). Without batching, each frame becomes a separate object, creating thousands of objects per layer. This value also matches the S3 multipart upload minimum part size.

Set a bucket lifecycle rule that aborts incomplete multipart uploads. A crash part way through completing a blob upload leaves one behind, and the server does not abort it.

If you previously configured a `path` that began or ended with a slash, move the existing objects to the normalized prefix before upgrading. A `path` of `registry/` stored keys under `registry//<project>/...` and now stores them under `registry/<project>/...`. A `path` containing any character outside `A-Za-z0-9._-/` is percent-encoded in the stored key (`team#1` becomes `team%231`), so data stored under such a prefix by the previous release needs the same move.
