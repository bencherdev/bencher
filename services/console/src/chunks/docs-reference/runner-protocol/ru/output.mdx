## Вывод Job

Когда Runner отправляет `completed` или `failed`,
вывод этого выполнения сразу сохраняется в том же OCI-хранилище, что используется для контейнерных Image,
по пути `{project}/output/v0/executions/{execution}`.
Когда у каждой итерации Job есть итог,
сервер собирает вывод Job из её выполнений в порядке итераций
и сохраняет его по пути `{project}/output/v0/jobs/{job}`.

Сохранённый вывод содержит массив `results` по каждой итерации и, в случае сбоя, строку `error`.
Каждая итерация записывает свой `exit_code`, `stdout`, `stderr`
и карту любых собранных выходных файлов с их содержимым.
При `allow_failure` итерация, чей запуск завершился с ошибкой, сохраняет только свои `exit_code` и `stderr`,
поэтому она сохраняет своё место, и ни одна Metric из неё не попадает в Report.
Вывод каждого выполнения разбирается [адаптером harness бенчмарка][adapters] сразу после сохранения,
и вывод, который нельзя прочитать, сразу завершает Job с ошибкой, даже при `allow_failure`.
После сохранения вывода Job сервер запускает [адаптер harness бенчмарка][adapters] по результатам,
чтобы разобрать Metric и Alert в Report, переводя Job в состояние `processed`.

Вывод возвращается при запросе Job через [API `GET /v0/projects/{project}/jobs/{job}`][job query api].
Тот же лимит `request_body_max_bytes`, что ограничивает сообщения WebSocket,
ограничивает размер вывода, который может доставить Runner.
