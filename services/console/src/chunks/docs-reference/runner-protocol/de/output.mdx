## Job-Ausgabe

Wenn ein Runner `completed` oder `failed` sendet,
wird die Ausgabe dieser Ausführung sofort im selben OCI-Storage-Backend gespeichert, das auch für Container-Images verwendet wird,
unter dem Pfad `{project}/output/v0/executions/{execution}`.
Sobald jede Iteration des Jobs ihr Ergebnis hat,
setzt der Server die Ausgabe des Jobs aus seinen Ausführungen in Iterationsreihenfolge zusammen
und speichert sie unter dem Pfad `{project}/output/v0/jobs/{job}`.

Die gespeicherte Ausgabe enthält ein `results`-Array pro Iteration und, im Fehlerfall, einen `error`-String.
Jede Iteration zeichnet ihren `exit_code`, `stdout`, `stderr`
und eine Zuordnung aller erfassten Ausgabedateien zu ihren Inhalten auf.
Mit `allow_failure` behält eine Iteration, deren Lauf fehlgeschlagen ist, nur ihren `exit_code` und `stderr`,
sodass sie ihren Platz hält und keine Metrics daraus in den Report gelangen.
Die Ausgabe jeder Ausführung wird mit dem [Benchmark-Harness-Adapter][adapters] geparst, sobald sie gespeichert ist,
und eine Ausgabe, die nicht gelesen werden kann, lässt den Job sofort fehlschlagen, auch mit `allow_failure`.
Nachdem die Ausgabe des Jobs gespeichert ist, führt der Server den [Benchmark-Harness-Adapter][adapters] auf den Ergebnissen aus,
um Metrics und Alerts in den Report zu parsen, wodurch der Job in `processed` übergeht.

Die Ausgabe wird zurückgegeben, wenn ein Job mit der [`GET /v0/projects/{project}/jobs/{job}`-API][job query api] abgefragt wird.
Dasselbe `request_body_max_bytes`-Limit, das WebSocket-Nachrichten begrenzt,
deckelt die Größe der Ausgabe, die ein Runner zustellen kann.

[job query api]: /de/docs/api/projects/jobs/#get-v0projectsprojectjobsjob
